## 1. 原始 LAN 威胁模型

审查针对的是「同一局域网内未授权的第三方」，而非公网攻击者。具体可被利用的情形是：
笔记本与手机（或任意同网设备、访客设备、被入侵的 IoT 设备）处于同一 Wi-Fi，
nav-server 在驾驶过程中持续广播车辆位置、目的地与路线。攻击者无需任何凭据即可：

- 读取实时导航状态（位置、速度、剩余里程、目的地）；
- **改写导航目的地**（`POST /api/route` 直接写 `pending_dest`，数据源线程下一帧即消费）；
- 读取 `dataset_dir` 的 Windows 绝对路径（泄露用户名与目录结构）。

显式排除在本轮之外：TLS/中间人、本机其他用户进程、供应链攻击、以及「把 nav-server 当作
公网服务器加固」。因此本轮不引入证书、不引入用户账户体系、不做速率限制框架。

## 2. 最终 listener / bind 模型

`TcpListener::bind(("0.0.0.0", port))` 无条件绑定所有 IPv4 接口的形态已移除。绑定地址由
`ExposureMode::bind_addr` 唯一决定：

| 模式 | 触发条件 | 绑定地址 | 令牌 |
| --- | --- | --- | --- |
| `LoopbackOnly` | 默认（无 `--lan`） | `127.0.0.1:<port>` | 不生成 |
| `Lan` | 显式 `--lan` | `0.0.0.0:<port>` | 启动时生成 |

`Lan` 仍绑 `0.0.0.0` 是 bind 的实现需要——无法只绑定「私网地址集合」，且网卡地址会在运行中
变化。**来源限制不依赖 bind 地址**，而是在 accept 之后按连接的实际对端地址执行（§3）。
这一分工由 `bind_addr_never_defaults_to_all_interfaces` 单测与 S1 集成断言共同锁定。

## 3. peer classification

`security::classify_peer(IpAddr) -> PeerClass` 为纯函数，是全部来源判定的唯一口径：

```
127.0.0.0/8    -> Loopback
10.0.0.0/8     -> PrivateLan
172.16.0.0/12  -> PrivateLan
192.168.0.0/16 -> PrivateLan
其他            -> Disallowed
```

判定按八位组显式匹配，并以 `classify_matches_std_is_private` 对 13×11×4×4 组地址与
`Ipv4Addr::is_private()` 交叉校验，防止「显式实现」与「惯用实现」在某个边界上分叉。
边界测试覆盖 `10.0.0.0/10.255.255.255/9.255.255.255/11.0.0.0`、
`172.15.255.255/172.16.0.0/172.31.255.255/172.32.0.0`、
`192.167.255.255/192.168.0.1/192.168.255.255/192.169.0.0` 与 `8.8.8.8`、`169.254/16`、
`100.64/10`、`0.0.0.0`、`198.18.0.1`。

**IPv6 明确记为未接入，不伪称已支持。** 当前 listener 只绑 IPv4，纯 IPv6 对端在传输层不可能
连入，故一律判 `Disallowed`——这是保守结果而非「支持后拒绝」。IPv4-mapped（`::ffff:a.b.c.d`）
按内层 IPv4 分类，使将来监听双栈时行为不退化为全拒。`classify_ipv6_is_conservative_not_claiming_support`
同时断言 `::1` **不得**因看似回环而被放行。

`Disallowed` 对端在 `handle_conn` 中于**解析任何请求内容之前**被拒绝：请求行与 headers 都不读，
未授权来源无法让服务端解析其构造的输入。

### 3.1 一个由该实现暴露的缺陷：早期拒绝的 403 会被 RST 吞掉

首次实现里 `Disallowed` 分支直接写 403 后返回。实测发现**同一地址三次连接中有一次**客户端收到
`WinError 10053`（连接被主机中止）而非 403：Windows 在仍有未读入站数据时关闭连接会发 RST，
可能把刚写出的响应一并丢弃。修复为写响应后有界排空入站字节（`drain_inbound`，上限 8192 B、
读超时 250 ms），排空只丢弃字节、不做任何解析，故「拒绝路径不解释请求内容」这一性质不变。
上限是必要的：否则对端可持续发送数据把拒绝线程钉住。

## 4. token generation / lifecycle

`SessionToken::generate()` 经 `getrandom` 调用 OS CSPRNG 取 32 字节 → 64 位小写十六进制。
256-bit 安全强度；hex 而非 base64 使 URL fragment 无需 percent 编码，测试断言也不必处理转义。
未使用时间戳、PID、计数器或自制 PRNG。

失败即**拒绝启动**（`--lan` 下令牌生成失败时 `exit(1)`），绝不降级为无令牌的 LAN 服务。
不持久化、不落盘；每次进程启动重新生成，旧令牌自然失效（S6 实测）。

`SessionToken` 刻意不派生 `Debug`，其 `Debug` 实现恒输出 `SessionToken(<redacted>)`，使令牌不
可能经 `{:?}` 意外进入日志或 panic 信息。启动横幅只报候选地址个数与模式，**不含令牌本体**。

**令牌相等比较**：`ct_eq` 逐字节累积差异后统一判定，避免按首个不同字节提前返回而泄露前缀匹配
长度；长度先判（令牌长度是公开信息，出现在二维码与前端校验中）。威胁模型为同 LAN 未授权访问，
32 字节随机令牌已提供足够熵，故未引入额外密码学框架。

## 5. loopback bootstrap 设计

`GET /api/lan-bootstrap` 是整个模型**唯一**的令牌出口：

| 条件 | 响应 |
| --- | --- |
| 非 `--lan` | `200 {"enabled":false}`，不生成也不返回令牌 |
| `--lan` + 回环对端 | `200 {"enabled":true,"port":N,"addresses":[...],"token":"..."}` |
| `--lan` + 私网/其他对端 | `403`，响应体不含任何令牌信息 |

令牌**不得**放进 `/api/metadata`、`index.html` 或 JS bundle：静态资源不鉴权（§11），放进去等于
取消鉴权。这一边界由 S2 与 S7 的「端点不回显令牌」断言共同锁定。

回环对端在 LAN 模式下**豁免令牌**是刻意的：本机 Browser/Tauri 需要先访问 bootstrap 才能拿到
令牌，若把本机客户端也强制走 LAN token 会形成自举死循环。该豁免由
`authorize_loopback_exempt_in_lan_mode` 单测与 E2E-LAN-03（回环服务器密码学无关地可连）锁定。

## 6. HTTP auth contract

请求处理顺序本身是安全语义的一部分：

1. 解析请求行 / headers；
2. `OPTIONS` → 仅对白名单 origin 返回许可头，否则 403 且无任何 CORS 头；
3. `/api/lan-bootstrap` → 回环限定（先于通用鉴权）；
4. `/api/*` → 默认拒绝式鉴权；
5. 业务路由；
6. 静态文件（不鉴权）。

第 4 步采用**前缀默认拒绝**：`/api/` 下一切路径都受保护，唯一豁免是 `/api/lan-bootstrap`。
任务书要求「至少保护」五个既有端点（snapshot / route / metadata / search / settings）；若按枚举
放行，将来新增的 `/api/*` 端点会默认处于未鉴权状态，按前缀拒绝则使新增端点默认安全。

HTTP API **只**接受 `Authorization: Bearer <token>`。`/api/route?token=...` 被显式拒绝（S3 断言
`401`）：query 会进入访问日志、浏览器历史、Referer 与诊断输出。WS 是唯一接受 query 令牌的通道，
因为浏览器 WebSocket API 无法设置请求头。

### 6.1 未授权请求的副作用

`POST /api/route` 写 `pending_dest` 的语句位于鉴权之后。S4 不只断言状态码：它以回环 WS 客户端
作为观测通道，先证明通道确实在收帧（否则负向断言无意义），再发未授权请求并断言**没有**
`map_state` 广播，最后以带正确令牌的请求作正向对照，断言广播确实发生且目的地为授权请求的目标
（`[-57000, 34500]`，而非未授权请求的 `[-52925, 36510]`）。没有正向对照，「无广播」可能只是
观测通道或路线本身不工作。

## 7. WS auth contract

浏览器 WebSocket API 无法设置 `Authorization` 头，故 LAN WS 使用 `/ws?token=<token>`，
同时接受 `Authorization` 头以方便原生客户端。

**鉴权严格先于 101**：无令牌或错令牌时返回 401，不发送 `101 Switching Protocols`、不把连接注册
进广播列表。不存在「先 101 再在第一帧鉴权」的形态。S5 断言远端无令牌与错令牌均为 401 且未完成
升级，正确令牌为 101 并实际收到 vehicle 帧流。

### 7.1 该实现暴露的第二个缺陷：服务端不回送 Close 帧

原实现的读循环收到 Close 帧后只 `break`，**不回送 Close**，违反 RFC 6455 §5.5.1（收到 Close 且
此前未发送过时「必须」回送）。后果是浏览器停留在 CLOSING 状态（实测 `readyState=2` 持续 8 s 以上），
`close` 事件不触发，于是 app.js 的重连排程根本不执行——用户主动断开后表现为「状态不变、也不重连」。
修复为回送 Close 帧并 `shutdown(Both)`（`ws_clients` 持有一份 socket 克隆，仅 drop 本函数内的
stream 并不会关闭连接）。

该缺陷**不会**由「杀掉服务器再重启」这类用例暴露：那属于 TCP 中止，`onclose` 会立即触发。
E2E-10（Batch 2 建立）正是这种形态，因此一直看不出问题。新增 E2E-10c 以客户端主动 `close()`
把它钉住；若回送被移除，该用例失败。

## 8. QR / token flow

二维码 URL 为 `http://<lan-ip>:<port>/#token=<token>`，使用 fragment 而非 query——fragment 不随请求
发送给 HTTP server，因而不进入访问日志。

移动端启动流程：读取 `location.hash` → 提取并校验令牌形态（64 位小写十六进制）→ 写入内存变量与
`sessionStorage` → 立即以 `history.replaceState` 从地址栏移除 fragment。无论令牌是否合法，
fragment 都会被抹掉；形态非法时记 WARN 并忽略，不静默当作「没有令牌」。不使用 `localStorage`
长期保存。server 重启后旧令牌自然失效。

### 8.1 二维码地址发现

原实现用 `location.hostname` 构造二维码地址，本机页面打开时得到 `http://127.0.0.1:<port>/`，
该二维码对手机无效（手机上的 `127.0.0.1` 指向手机自己）。现由服务器枚举实际候选地址。

**未采用「按路由选主 IP」的常见做法**，因为在本机实测中它给出错误答案：以 UDP connect 探测
`8.8.8.8` 时 OS 选用的源地址是 `198.18.0.1`（VPN 隧道），据此生成的二维码指向隧道地址，手机
不可达。因此改为枚举全部 RFC1918 候选并按 `(active, 地址数值)` 排序——排序键完全确定，同一组
输入必得同一顺序。

**未采用网卡名启发式**（如「含 Wi-Fi 者优先」）：在 Hyper-V / VPN / WSL 并存时会给出一个自信但
错误的静默选择。候选集与 `classify_peer` **同源**（复用同一函数），因此二维码给出的地址必然是
服务端自己愿意接受的 `PrivateLan` 类别——否则会出现「扫了码连不上、且原因是服务端拒绝该来源」
的荒唐情形。该不变量由 `discovered_candidates_are_all_classified_private_lan` 锁定。

本机实测候选为 `10.148.63.202`（Wi-Fi，preferred）与 `172.30.0.1`（vEthernet (Default Switch)），
两者均为 active，服务器返回全部候选并标注网卡名，候选多于一个时 UI 显示下拉框由用户选择。

### 8.2 令牌不进入可见 DOM 与测试 artifact

二维码的可见文本只显示 `http://<addr>:<port>/`；含令牌的完整 URL 保存在
`canvas.dataset.qrTarget`。理由：令牌出现在失败截图、Playwright trace 等 artifact 中没有任何
价值，而它已通过二维码本身交付给手机。E2E 经 `data-qr-target` 断言二维码内容。
E2E-LAN-01 显式断言 `#qr-url` 文本**不含**令牌。

## 9. CORS / Tauri origin 策略

通配符 `Access-Control-Allow-Origin: *` 已从两条响应路径（普通与静态）完全移除。

**实测而非记忆**：Tauri 源未经推测确定。`desktop/tauri.conf.json` 为 Tauri 2（`$schema`
`config/2`，`tauri` crate 2.11.5），只有 `frontendDist`、无 `devUrl`，故 dev 与 prod 均走自定义
协议。为取得真实 Origin，在 `127.0.0.1:8123` 起一个捕获握手的探针，运行已构建的
`desktop/target/debug/ets2nav-desktop.exe`，捕获到：

```
GET /ws HTTP/1.1
Origin: http://tauri.localhost
```

因此白名单为 `CORS_ALLOWED_ORIGINS = ["http://tauri.localhost"]`，且**仅此一项**。刻意未加入
下列「记忆中的」候选，因为它们在本项目当前配置下未被验证：`tauri://localhost`（macOS/Linux
形式）、`https://tauri.localhost`、`http://localhost:1420`（Tauri 默认 devUrl，本项目未配置）。

未命中白名单（含无 `Origin`、含 `null`）→ 返回**空表**，即不发出任何 `Access-Control-*` 头。
命中时发出的值**取自白名单常量本身**而非请求里的字面量：二者内容相同，但向前者取值的写法使
「响应头中不可能出现请求方构造的字节」成为结构性事实，无需再论证 CRLF 注入不可行。
白名单响应带 `Vary: Origin`，否则会被共享缓存串用。

`OPTIONS` 预检仅对白名单 origin 生成，`Allow-Methods: GET, POST, OPTIONS`、
`Allow-Headers: Authorization, Content-Type` 逐项列举，不使用 `*`；非白名单 origin 返回 403 且
**不返回任何 CORS 许可头**（含 `Allow-Methods`/`Allow-Headers`）。

**Origin 不是 authentication**：CORS 头只决定浏览器是否把响应交给调用方，不构成访问控制；
非浏览器客户端完全不受 CORS 约束。因此令牌鉴权独立存在，且 S3 显式断言「伪造
`Origin: http://tauri.localhost` 的远端请求仍为 401」。

## 10. metadata privacy 改动

`{"dataset": ctx.dataset_dir}` 会返回完整绝对路径（形如 `<盘符>:\<用户目录>\...\data\europe-v5`），
把开发机用户名与目录结构泄露给任何能访问该端点的对端。现返回
`{"dataset":"europe-v5","edges":696849,"nodes":360717}`——只用**目录名**，不返回路径。
`dataset_dir` 在进程内部照常保留用于加载与日志。

`metadata_json` 被抽为纯函数以便直接断言隐私性质：测试对 Windows/Unix 两种风格、含盘符与不含
盘符的输入，断言输出不含完整路径、不含 `:\`、不含 `/` 或 `\`、不含 `users`/`projects` 段。

## 11. S1–S9 结果

集成套件 `tools/ets2nav-web/verify-lan-security.py` 全部断言都打在真实运行的 `nav-core-cli server`
进程上，经真实 TCP/HTTP/WS 连接。**关键手法**：从本机连到自己的私网地址时，内核选用的源地址
就是该私网地址，因此服务端看到的对端**确实**是 `PrivateLan`——单机即可真实执行远端来源矩阵，
无需第二台设备，也没有任何桩件伪造来源。

判定机制本身先经 `--selftest`（8 项）验证：解析器、通配符检出、204 空体等。

| 组 | 结果 | 说明 |
| --- | --- | --- |
| S1 默认 bind | PASS | 回环 200；私网地址 `CONN-FAIL`（连接被拒，非 403） |
| S2 LAN bootstrap | PASS | 回环授予令牌；远端 403 且不泄露令牌 |
| S3 API auth | PASS | snapshot/route 无令牌 401、错令牌 401、正确令牌 200 |
| S4 route 副作用 | PASS | 未授权无广播；正向对照确认授权请求真的改变目的地 |
| S5 WS auth | PASS | 远端无/错令牌 401 不升级；正确令牌 101 且收到帧流 |
| S6 令牌轮换 | PASS | 每次启动不同；旧令牌在新进程上 401 |
| S7 metadata 隐私 | PASS | 无绝对路径；端点不回显令牌 |
| S8 CORS | PASS | 同源/白名单/未批准/预检分别验证；全端点无通配符 |
| S9 Disallowed 来源 | PASS | 经本机 `198.18.0.1` 真实执行 |

S1 的第二项判据是**连接被拒**而非 403：只绑 `127.0.0.1` 时私网地址在 TCP 层就不可达，
`CONN-FAIL` 才是正确形态。断言 403 反而是错的。

**S9 从「NOT VERIFIED」变为实测。** 首轮运行如实记录 `NOT VERIFIED`，理由是「本机无法构造公网
源地址」。随后排查发现该理由不成立：本机 VPN 隧道地址 `198.18.0.1` 既非回环也非 RFC1918，
服务端判为 `Disallowed`，且可连接（链路本地 `169.254/16` 则 `WinError 10065` 不可达，被探测
筛除）。因此改为枚举本机非 RFC1918 的非回环地址、逐个探测连通性，用真正会被判 `Disallowed` 的
地址执行断言。最终 `FAIL=0 NOT_VERIFIED=0 SKIP=0`，退出码 0。

## 12. E2E-LAN 结果

新增 `tests/e2e/12-lan.spec.mjs`，8 项全部通过。手法同 S9：从
`http://10.148.63.202:<port>/` 打开页面，使服务端看到真实的私网对端。

| 用例 | 断言要点 |
| --- | --- |
| E2E-LAN-01 | 二维码地址为 RFC1918 且属服务器候选、非回环；fragment 为 `#token=<64hex>` 且等于服务端当前令牌；可见文本不含令牌 |
| E2E-LAN-01b | 多候选时全部列出（含网卡名），切换地址重绘二维码；单候选时不显示选择器 |
| E2E-LAN-02 | fragment 被读取、写入 sessionStorage 与内存、地址栏 hash 被清除 |
| E2E-LAN-02b | 畸形令牌被拒绝、不写 session、不附加到 WS URL，连接失败 |
| E2E-LAN-03 | WS URL 恰为 `ws://<lan-ip>:<port>/ws?token=...`，**不含** `127.0.0.1`/`localhost`，且真实收到帧 |
| E2E-LAN-04 | UI 点击产生的 `/api/route` 请求带 `Authorization: Bearer <token>` 且 200；清除令牌后同一操作 401 且无 auth 头 |
| E2E-LAN-05 | 客户端主动断开后重连，每次连接都带同一令牌与同一 LAN 主机 |
| E2E-LAN-05b | 服务端重启后旧令牌失效，页面不进入「已连接」，且重连未丢失令牌参数 |

E2E-LAN-03 是本批的关键回归测试：它锁定 PLAN-P3plus B5 的阻断项——页面按同源推导 WS 地址，
与主机是否回环无关。

**测试自身的两处不稳定已修复，不记为产品缺陷：**

其一，E2E-LAN-05/-05b 原先轮询 `#conn-status` 文案断言断线提示，但该提示只存在约 1 秒（退避基数
1 s，随后被「连接中…」「已连接」覆盖），轮询会随机漏掉。改为 `MutationObserver` 累积全部文案
变化，「曾向用户报告断线并排程重连」因而成为确定性事实。

其二，Playwright 配置增加 `--no-proxy-server`。LAN 用例依赖「浏览器直连私网地址使服务端看到
私网对端」这一前提；若浏览器把请求交给系统代理，服务端看到的对端会变成回环并从豁免路径通过，
用例会悄然测错对象。本机系统代理的 bypass 列表恰好覆盖 `10.*/172.16-31.*/192.168.*`，但那是
巧合而非保证，故显式禁用代理，使结果不依赖开发机的代理配置。

### 13.1 该验证自身暴露的一个陷阱（值得记录）

首轮运行 M1/M2/M3 的 **restored 也是 exit 1**，四项判定全 FAIL。原因不在被测代码：`Copy-Item`
还原文件时会**连同原始 `LastWriteTime` 一起还原**，而该时间早于用变异源码构建出的产物，cargo
因此判定 crate 未变、**不重新编译，静默保留变异二进制**。当时直接验证确认：源文件哈希已与备份
一致，而二进制仍在返回 `Access-Control-Allow-Origin: *`。

这是「源码已还原但产物仍是变异的」这类静默分歧——若只看源码 diff 会得出完全错误的结论。
修复为还原时以 `Get-Date` 触碰文件强制重建，并新增 `Assert-FreshArtifact`：每次 `cargo build`
后断言二进制时间不早于其源文件，否则抛出。加固后四项全部 PASS，且产物经 `npm run test:security`
复验为干净（`LAN SECURITY: PASS`）。

顺带记录：该脚本历经两次 PS 5.1 解析失败——第一次因在 match anchor 里引用了含中文的源码注释，
而 `.ps1` 无 BOM 时被按 ANSI 读取，非 ASCII 字节被错误解码导致解析崩溃。脚本内已写明
「ASCII-only，且所有 anchor 也必须是 ASCII」。

# 附录 A — 2026-09-12 追补：独立复审发现的 browser-mediated loopback gap

**本节为追补，上文 §1–§18 的历史结论一律保留、不作改写。** 上文把
`PeerClass::Loopback` 的无条件放行写作「刻意的设计」，并据以给出 `P4 LAN security gate = PASS`；
该判断在**当时所列的威胁模型内**（同局域网未授权第三方）成立，但没有覆盖「用户浏览器被诱导
访问恶意页面」这一来源。独立复审指出该缺口，Batch 3.5 以真实 Chromium 复现并修复。

## A.1 概念错误：peer-address authentication ≠ request-intent authentication

```
TCP 对端 = 127.0.0.1      ⟹  连接由本机某进程建立
TCP 对端 = 127.0.0.1      ⇏  请求意图来自可信的本地页面/程序
```

浏览器是用户机器上的一个进程，因此**恶意页面可以让浏览器替它向 `127.0.0.1` 发起请求**，
服务端看到的对端地址同样是回环。上文 §6 的规则表（`Loopback → Allowed`）因此把「对端地址」
误当作「身份」使用，使漏洞面从 bootstrap 扩大到全部动态 API 与 `/ws`。

Batch 3.5 实测复现（真实 Chromium，攻击页面与 nav-server 同机不同端口）：

```
CONFIRMED CSRF   跨源 simple POST（Content-Type: text/plain，无 preflight）
                 把导航目的地从 [-58456,32832] 改写为 [-52925,36510]（经服务端 map_state 广播观测）
CONFIRMED CSWH   跨站 WebSocket 成功升级并收到 77 个车辆帧
```

## A.2 修正后的模型（取代上文 §5–§7 的规则部分）

| 机制 | 决定什么 | 依据 |
|------|----------|------|
| `classify_peer` | 是否允许建立连接、能否取得令牌 | TCP 对端地址 |
| `SessionToken` | 是否允许调用动态 API 与 `/ws` | 256-bit 随机凭据（**两种模式下都存在**） |
| `ServerAuthorities` | 浏览器 Origin/Host 是否属于本服务器 | 实际监听端口 + 本机实际地址 |

对端类别继续用于暴露面控制、bootstrap 资格与 LAN 来源限制，**不再作为免令牌理由**。
`/api/bootstrap`（原 `/api/lan-bootstrap`）是唯一的动态 API 豁免，且该豁免自身受
「回环对端 + Origin 合规」双重限制。详见 `p4r-batch35-2026-09.md`。

## A.3 文案勘误（§8 措辞）

上文 §8 与 §12（E2E-LAN-01）称二维码完整 URL「仅存于 `canvas.dataset.qrTarget`」，并据此写作
「令牌不进入可见 DOM」。该表述不准确：

- `dataset` **仍然属于 DOM**，只是不以可见文本呈现，同源脚本与测试工具都能读到；
- 令牌同时存在于页面 JS 变量、`sessionStorage` 与 QR canvas 状态中——这是客户端建立认证
  连接的必要条件，不是可以消除的冗余。

准确表述应为：**令牌不以可见文本展示**；它仍存在于页面 JS 状态、`sessionStorage` 与 QR
canvas 状态中，并可能因此出现在失败截图与 Playwright trace 等测试 artifact 里。
这不是新的安全 blocker，仅修正上文对「不进 DOM」的表述强度。

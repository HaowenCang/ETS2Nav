# P4R Batch 3.5 — Browser-to-Loopback / CSRF / CSWH 加固（2026-09）

**结论**

```
Browser-to-loopback HTTP security = PASS
Cross-site WebSocket security     = PASS
P4 LAN security gate              = PASS（由 REOPENED 恢复）
```

本轮由独立复审触发，起点是一个**已被真实复现**的漏洞类别而非推测风险：Batch 3 把
`PeerClass::Loopback` 当作身份，使「TCP 对端是 127.0.0.1」等价于「已认证」。修复的核心是
把**对端地址**（暴露面控制）与**会话令牌**（身份）拆成两层，并把浏览器 `Origin` / `Host`
从「CORS 输出参数」提升为独立的准入判定。

## 1. 先复现，再修改

### 1.1 复现方法

攻击面必须用**真实浏览器**验证：Python/Node 的 HTTP 客户端本就不受同源策略与 CORS 约束，
用它们「模拟浏览器」无法证明任何事。因此建立了一个与 nav-server **同机不同端口**（即跨源）
的攻击页面服务器，用 Playwright 锁定的真实 Chromium（`153.0.8010.12`，revision 1243）加载
它并执行攻击。

副作用判定不依赖攻击页面看到的响应——`no-cors` 下跨源请求恒返回 opaque 响应
（`type:"opaque", status:0`），服务端接受或拒绝都一样。判据打在服务端**真实广播**上：
以一条已认证的 WS 连接观察 `map_state` 事件中的 `destination`。

复现脚本：`tools/ets2nav-web/scripts/repro-browser-loopback.mjs`（可重跑，修复前后各执行一次）。

### 1.2 结果：`CONFIRMED CSRF`

修复前（`60124fe`，默认回环模式，未加 `--lan`）：

```

```


攻击页面用 `mode:"no-cors"` + `Content-Type: text/plain`（属 CORS safelisted 类型，
不触发 preflight），把导航目的地从 A 改写为 B。服务端不检查 `Content-Type`，直接把
`text/plain` 的 body 当 JSON 解析并写入 `pending_dest`。**副作用确实发生**，且从回环来源与
RFC1918 来源两个攻击页面 origin 都能触发。

### 1.3 结果：`CONFIRMED CSWH`

同一次运行中：

```
cross-site WebSocket: {"frames":77,"opened":true,"error":null,
                       "origin":"http://127.0.0.1:12926","closeCode":1005}
WebSocket CSWH     : CONFIRMED CSWH
```

跨站 WebSocket 完成 101 升级并收到 77 个车辆帧。WebSocket 不走 CORS preflight，因此这一
路径**完全依赖服务端自行校验 Origin 与身份**，而修复前的服务端两者都没做（回环无令牌、
握手不校验 Origin）。

### 1.4 浏览器平台额外保护的观察（不作为判据）

同一攻击页面的 `application/json` 跨源 POST 被阻断：

```
JSON POST (application/json): {"ok":false,"error":"TypeError: Failed to fetch"}
控制台: Access to fetch ... has been blocked by CORS policy:
        Response to preflight request doesn't pass access control check
```

阻断来源是**服务端自身的 CORS 预检拒绝**（非白名单 origin 无 `Access-Control-Allow-Origin`），
不是浏览器平台缓解。simple POST 与跨站 WS 两条路径在本次实测中**未观察到任何平台级缓解**。

实测覆盖的 origin 组合为 `http://127.0.0.1:<其他端口>` → `http://127.0.0.1:<nav端口>` 与
`http://<本机 RFC1918>:<其他端口>` → 同上。**由公网 origin 发起的请求未在本环境实测**
（本机没有可用的公网 origin）。这一空缺不影响结论，因为 §21 的要求正是「即使浏览器愿意把
请求发出去也必须安全」——服务端模型不依赖任何浏览器版本特性。

## 2. 修正后的认证模型

```
bootstrap 端点              → 特例（唯一豁免，回环 + Origin 双重限制）
其余全部受保护动态 API      → 必须携带有效会话令牌
/ws                        → 必须携带有效会话令牌 + Origin 合规
```

`peer classification` 保留，但职责收窄为：网络暴露控制、bootstrap 资格、LAN 来源限制。
**它不再是免令牌的理由。**

| 模式 | Loopback | PrivateLan | Disallowed |
|------|----------|------------|------------|
| `LoopbackOnly` | 令牌正确→Allowed | Forbidden | Forbidden |
| `Lan` | 令牌正确→Allowed | 令牌正确→Allowed | Forbidden |

`security::authorize` 的签名由 `expected: Option<&SessionToken>` 改为 `expected: &SessionToken`：
令牌在**两种模式下**都生成，「无令牌的服务」在类型层面不再可表示。生成失败一律
`exit(1)`，绝不降级。

自举死循环如何避免：本机页面同样拿不到令牌，因此需要一个唯一且仅对回环开放的令牌出口。
这正是 §3 的 bootstrap，而不是「回环免认证」的一般化通道。

## 3. bootstrap contract

端点由 `/api/lan-bootstrap` 更名为 **`/api/bootstrap`**，语义从「LAN 令牌引导」提升为
「会话引导」。旧名不保留别名：第二个入口只会多出一条需要独立审计的豁免路径，且新增单测
断言 `/api/lan-bootstrap` 落回**默认拒绝**（S1：无令牌 401）。

响应（两种模式同形，`addresses` 恒存在）：

```json
// LoopbackOnly
{"lan_enabled": false, "port": 8123, "addresses": [], "token": "<64 hex>"}
// Lan
{"lan_enabled": true,  "port": 8123, "addresses": [{"address":"10.148.63.202",
                          "interface":"Wi-Fi","active":true,"preferred":true}], "token": "<64 hex>"}
```

三重限制，缺一不可：

1. **对端必须是回环**。远程对端 403，响应体不含令牌与候选地址——手机不能从服务端取令牌，
   只能经二维码 fragment 接收。
2. **若请求携带 `Origin`，该 Origin 必须合规**：只能是本服务器自身的同源页面，或 CORS
   白名单（实测 `http://tauri.localhost`）。`Origin: null` 必然落到「不在表内」被拒。
3. **响应硬化**：`Content-Type: application/json`、`Cache-Control: no-store`、
   `X-Content-Type-Options: nosniff`、`Referrer-Policy: no-referrer`；403 与 200 走同一
   输出路径，不存在「拒绝路径漏掉硬化头」的分支。

`Origin` 不是非浏览器客户端的认证手段——原生客户端可以省略或伪造它。因此 bootstrap 的真正
门是第 1 条；第 2 条是对**浏览器场景**的附加约束，二者是两层不同机制而非互相替代。

`--lan` 未启用时不再枚举局域网候选：默认模式 listener 只绑 127.0.0.1，任何非回环地址都不可能
连入，枚举既无用，又会让 `lan_enabled:false` 与「返回了可用地址」自相矛盾。

## 4. HTTP Content-Type policy

`POST /api/route` 之外，策略按**方法**而非端点生效：`/api/` 下一切 `POST`/`PUT`/`PATCH` 都必须
声明 `Content-Type: application/json`（允许 `; charset=utf-8` 等参数），否则 **415
Unsupported Media Type**。按方法而非端点枚举，使将来新增的写入端点默认继承该约束。

执行顺序为「鉴权 → 媒体类型 → 解析」：未授权请求仍先得到 401；携带正确令牌但声明
`text/plain` 的请求得到 415，`text/plain` 的 body 不再被当作 JSON 执行。

这不是令牌的替代品，而是纵深防御：浏览器只对 CORS safelisted content type 允许无 preflight
的跨源发送，因此要求 `application/json` 使跨源写入在**预检层**就不可达，而不只依赖令牌。

## 5. WebSocket Origin policy（`/ws`）

握手校验顺序本身是安全语义：

```
对端类别（连接层） → Origin（若存在） → 令牌 → 101
```

- **Origin 合规**：authority 属于本服务器（回环名或本机实际地址 + 实际端口，scheme 必须为
  `http`，服务端无 TLS），或命中 CORS 白名单。
- 恶意 Origin → **403，且不发送 101**；令牌尚未参与判定，因此这一步独立于令牌。
- 无 `Origin` → 按原生客户端处理，**仍必须持有有效令牌**。
- 令牌通道：浏览器用 `/ws?token=<token>`（WebSocket API 无法设置请求头），原生客户端可用
  `Authorization: Bearer`。

`Origin` 检查刻意**先于**令牌，否则它会退化成一个只对「没有令牌的攻击者」有效、被令牌完全
覆盖的装饰性检查。该性质由 BLS-04 与 S11 各自断言：**持有正确令牌 + 恶意 Origin 仍 403**。

## 6. Host validation policy

### 6.1 为什么必须独立于 Origin 判定

若同源判定写成 `Origin == Host`，则攻击者把域名解析到 127.0.0.1 后（DNS rebinding），
`Host: evil.example` + `Origin: http://evil.example` 会**自洽通过**。因此：

- 可接受 authority 集合**只来自服务器自身状态**：回环名（`127.0.0.1` / `localhost` / `::1`）
  与本机实际接口地址，端口为 listener 的实际端口；
- 同源 Origin 判定**不与 `Host` 比对**，只查上述集合；
- `Host` 单独校验，且在任何依赖 authority 的判定之前执行。

### 6.2 契约

- 缺失 `Host`、`Host` 为外部域名、端口不符、端口段畸形（`127.0.0.1:8a`）→ **403**，
  响应体回显经 JSON 转义且长度上限 64 的 authority（诊断用，不构成反射通道）。
- 校验覆盖**所有**请求：动态 API、bootstrap、`/ws` 握手与静态资源。
- 默认端口语义：`Host` 未写端口时按 80 处理，仅当实际监听端口为 80 时命中。

### 6.3 可用性代价与缓解

以本机主机名/组播名（如 `mypc.local`）访问不再被接受，必须使用回环名或二维码/设置面板给出的
实际 IP。为降低「DHCP 换址或网卡后启用导致正常客户端被拒」的风险，`Host` 未命中时会**重新
枚举一次网卡**再判，限频 1 秒。刷新不削弱安全性：接受集合始终是「本机接口的实际地址 + 回环
名」，攻击者控制的域名永远无法进入该集合。

## 7. Browser / Tauri / Mobile 令牌流程

```
页面加载
 ├ fragment 携带 token（校验 64 位小写十六进制）
 │    ├ 合法 → 写入内存 + sessionStorage，立即 replaceState 抹除 fragment
 │    └ 畸形 → 告警并**按没有 fragment 处理**（继续走后续来源）
 ├ sessionStorage 命中 → 使用
 └ 以上皆无，且基址主机是回环（本机浏览器 / Tauri）→ GET /api/bootstrap 取令牌
      └ 手机（LAN 地址）→ 不尝试 bootstrap：服务端必然 403，令牌只能经二维码交付
 ↓
全部 API 经 apiFetch 携带 Authorization: Bearer；WS 由 connect() 在构造 socket 时附加当前令牌
```

`connect()` 仍为同步：令牌必须在**构造 socket 之前**就位，否则首次连接必然 401、页面先显示
一次「已断开」再重连——那是引导时序缺陷被当作正常现象。

**重连**（§17）：每次重连前先尝试刷新令牌。令牌是**进程级**的，服务端重启后旧令牌必然失效；
本机页面（回环）可以重新引导取回新令牌，因此具备自愈能力；LAN 手机端不能（服务端对非回环
一律 403），只能重新扫码——这是「令牌出口仅限回环」的必然结果，不是缺陷。

**apiFetch**：修复后回环页面的请求同样携带 Bearer，不因「本机」而免令牌。

## 12. 新发现问题

**12.1（本轮核心，已修复）** 回环对端免令牌，使漏洞面从 bootstrap 扩大到全部动态 API 与
`/ws`。真实 Chromium 复现：`CONFIRMED CSRF`（跨源 simple POST 改写导航目的地）与
`CONFIRMED CSWH`（跨站 WebSocket 读取 77 个车辆帧）。

**12.2（同源风险，已结构性消除）** 服务端此前**完全没有 Host 校验**。若后续把同源判定写成
`Origin == Host`，DNS rebinding 场景下二者会自洽通过。现改为：可接受 authority 集合只来自
服务端自身状态，同源判定不与 `Host` 比对，且 `Host` 单独校验。

**12.3（契约一致性问题，本轮引入并当轮修正）** 实现过程中一度让默认模式也枚举局域网候选，
结果是 `lan_enabled:false` 与「返回了非空 `addresses`」并存——UI 若据此绘制二维码会给出一个
连不上的地址。由 S1 断言「默认模式 bootstrap 不下发局域网候选地址」捕获并修正为「仅 `--lan`
时枚举」，`refresh_addresses` 亦限定在 `Lan` 模式。

**12.4（测试自身的静默空断言，已修复）** `verify-server-protocol.py` 的非法 JSON body 检查
只计算不判定（见 §11）。

**12.5（构建/就绪探测的可诊断性，已改进）** 服务端在 `TcpListener::bind` 之后、accept 循环
之前还要读取 `search.db`，因此「端口已绑定」与「已可服务」不是同一件事；原先的就绪探测既
无法区分二者，失败时也只报「未监听」。现改为以 `/api/bootstrap` 返回合法令牌为就绪判据，
并在失败信息中给出**最后一次探测的实际结果**、进程退出码、等待时长与启动参数。

本轮观察到两次不可解释的启动/就绪异常（一次 `--lan` 服务已打印 listening 但 45 s 内探测
未成功；一次测试内 `startServer` 超过该测试的 60 s 预算）。两项在随后 8/8 轮的专项压力复现
（原始 socket 探测与 fetch 探测并行）与最终多次全量运行中均未再现；服务端就绪实测约
2.4–2.6 s/进程。**未确定根因**，已按上述方式使再次出现时可归因，并据此把测试内的服务器预算
按「启动两个进程」的实际需要显式放宽（断言未放宽）。

**12.6（既有 flake，本轮细化了机理，未修复——§24 明确排除）** E2E-09「拖拽暂停跟随」偶发
失败。本轮取证结果：

- 输入事件本身正确：MapLibre 收到的 `mousedown` 为 `button=0, buttons=1, target=CANVAS`，
  `map.dragPan.isEnabled() === true`，9 个 canvas 级 `mousemove` 全部送达；
- 但 MapLibre 的拖拽状态机**未进入拖拽态**，`dragstart`/`dragend` 均未发出，取而代之发出了
  `click`；即应用层的 `pauseFollow` 从未被调用，`following` 因此保持 `true`；
- **A/B 实测**（同一份用例、同一轮环境、仅替换前端产物，各 8 次）：
  Batch 3 的 `app.js` **3/8** 失败，Batch 3.5 的 `app.js` **4/8** 失败——差异在噪声范围内，
  **不是本轮引入的回归**；
- 本轮 `npm run test:e2e` 三次尝试中两次失败于该项（另一次 43/43 通过），全量套件下的触发率
  高于 Batch 3 记录的单次观察，但其机理与 Batch 3 报告 §14.1 记录的同一处竞争一致。

该现象位于第三方库的拖拽起始路径，本轮不改动其代码路径（`app.js` 的
`following`/`followPausedAt`/`resumeFollow`/`easeTo`/`dragstart`/`wheel` 一行未动）。

**12.7（既有形态，已记录）** WS 令牌经 query 传递，因而会出现在浏览器开发者工具的网络记录
与 Chromium 自身的控制台错误文本中（实测：`WebSocket connection to 'ws://…/ws?token=…' failed`）。
这是「浏览器 WebSocket API 无法设置请求头」的直接后果，无法在保持浏览器可用的前提下消除；
缓解手段是令牌为进程级、重启即失效，且不以任何形式进入服务端日志。

## 13. 剩余风险

按影响从高到低：

**静态资源不鉴权**（刻意的威胁模型决策，未改变）。手机必须先取到客户端代码才能读取 URL
fragment 中的令牌，因此 `/`、`index.html`、`app.js`、`style.css`、`manifest.json`、
`map.pmtiles` 仍免令牌。本报告据此**不**声称「LAN 服务全部资源均需认证」；防护目标是动态
导航状态与控制 API。跨源页面可以**加载**这些资源，但读不到任何动态状态。

**无 TLS**。同一局域网内的被动嗅探者仍可获知令牌（HTTP 与 WS 均为明文）。本轮不引入证书
体系；风险与「同 LAN 被动嗅探」这一前提绑定。

**令牌的存在位置**（§A.3 勘误对应）：页面 JS 变量、`sessionStorage`、QR canvas 的 `dataset`
与 WS query。可见文本中不出现，但它并非「不在 DOM 中」。

**无速率限制**。bootstrap 仅对回环开放且对跨源 Origin 一律 403，因此不构成放大面；但若
将来的威胁模型纳入「本机其他用户进程」，需要重新评估。

**Host 校验的可用性代价**：以本机主机名访问不再被接受（§6.3）。

**IPv6 未接入**：纯 IPv6 对端一律 `Disallowed`，这是保守结果而非「已支持后拒绝」。

**MapLibre 安全公告未处理**（`maplibre-gl <= 6.4.0`，修复需跨 major 升级）。本轮范围是
network/auth/CORS，不含依赖迁移。

**绿灯窗口 GLOSA 不可达**（P3 记录，由 E2E-07e 固定为已知缺口，本轮未触碰）。

**E2E-09 拖拽 flake**（§12.6，§24 明确排除）。

**服务端启动期间不可服务**（§12.5）：listener 已绑定但尚未进入 accept 循环，此窗口内连接的
客户端会超时。这是既有形态，非本轮引入；本轮只改进了探测与可诊断性。

**LAN 手机端在服务端重启后需重新扫码**：令牌轮换 + 非回环不得 bootstrap 的必然结果。

## 16. Batch 4 前置约束（在 Batch 3 §18 基础上追加）

Batch 3 §18 的约束继续有效（`--fake-signal` 不得移除或绕开；Tauri origin 变更须重新实测）。

新增：

1. **不得以「对端是回环」为由豁免任何动态 API 或 `/ws`。** 该豁免是本轮修复的漏洞本体，
   新增测试断言（BLS-08、S3b）与 mutation M1 会同时失败。
2. **新增动态端点默认继承令牌要求与 JSON 媒体类型约束**（`is_protected_api` 按前缀拒绝、
   `body_must_be_json` 按方法判定），不得为新端点单独开豁免。
3. **新增浏览器可见的端点若接受 `Origin`，必须使用 `browser_origin_accepted`**（同源集合来自
   `ServerAuthorities`，不得与请求自报的 `Host` 比对）。
4. **`/api/bootstrap` 是唯一令牌出口**；若 Batch 4 需要新的引导路径，必须并入该端点而不是
   新增豁免，否则 `is_protected_api` 的默认拒绝语义与 S1 断言会失效。
5. 若 Batch 4 引入本机主机名访问（mDNS 等），**必须同时扩充 Host/Origin 接受集合**，
   不得为便利而放开 `Host` 校验。

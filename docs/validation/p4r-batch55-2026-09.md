## 2. 三个失败的原始证据与分类

三个现象此前被合并描述为"等待型正向前置在窗口内没有出现"。这一描述是准确的，但它没有定位任何东西——"等待没等到"是症状而不是原因。逐条重新取证后，三者的机制并不相同。

`E2E-07b`（run [34685268396](https://github.com/HaowenCang/ETS2Nav/actions/runs/34685268396) @ `8a51467`，`1 failed / 44 passed (4.6m)`）：

```text
  x  14 tests\e2e\07-glosa.spec.mjs:85:1 › E2E-07b 信号消失后旧 GLOSA 不残留 (5.5s)
    Error: expect(received).not.toBeNull()
    > 94 |   expect(parseGlosa(shown)).not.toBeNull();
```

等待本身**成功了**（5.5 s 就结束，远未触及 30 s 上限），失败发生在等待返回之后的解析上。这是一个判别性很强的事实：它不是"没等到"，而是"等到的东西取回来变了"。

`E2E-06`（run [34685594247](https://github.com/HaowenCang/ETS2Nav/actions/runs/34685594247) @ `7a65dac`，`1 failed / 44 passed (7.9m)`）：

```text
  x  11 tests\e2e\06-signal.spec.mjs:22:1 › E2E-06 信号卡片覆盖 Red / Yellow / Green / 无信号 (1.3m)
    Error: page.waitForFunction: Test timeout of 60000ms exceeded.
    > 15 |   await page.waitForFunction((want) => {
```

这是在 `waitForFunction` 内部耗尽**整个用例**的 60 s 预算，而不是耗尽某个等待自己的 40 s 上限。同一套件里该用例在绿色运行中的耗时是 **31.7 s**（run [34686319010](https://github.com/HaowenCang/ETS2Nav/actions/runs/34686319010) @ `12c3dbc` 的日志）。二者合起来说明该用例的正常耗时就已在 30 s 量级、且方差足以越过 60 s。

`BLS-01`（run [34684780069](https://github.com/HaowenCang/ETS2Nav/actions/runs/34684780069) @ `98d199b`，Security Portable failure 276 s）：

```text
  x  1 tests\e2e\13-loopback-security.spec.mjs:190:1 › BLS-01 跨源 simple POST（text/plain）无法改写导航目的地 (33.7s)
    Error: 正向对照必须成功，否则负向断言无区分力
```

BLS-02 在**同一轮里用同一目的地 C** 于 6.7 s 通过，BLS-03..09 全绿。失败落在"观测通道是否真的活着"这一对照上，而当时的失败信息里没有任何通道状态——`closed`/`errored` 诊断是随后一次提交才补上的，因此这一次的原始证据永久缺失。这一点必须如实记录：**BLS-01 的根因没有被直接观测到**，本轮的处置是重新定义判定对象而不是"修好了那个 bug"（§8）。

按 §2 要求的六分法归类：

| 现象 | 分类 | 依据 |
| --- | --- | --- |
| E2E-07b `parseGlosa(shown) === null` | **TEST ORACLE RACE** | 等待 5.5 s 即返回，取值与判定分处两次浏览器往返 |
| E2E-06 60 s 超时 | **TEST SYNCHRONIZATION DESIGN** | 等待顺序固定为 Red→Green→Yellow，与剧本相位序列不一致，正常耗时已达 31.7 s |
| BLS-01 正向前置失败 | **PRODUCT / SESSION PROCESSING FAILURE** | 见 §2.1：服务端数据源线程 panic（首个 PR 运行由新增的 stderr 诊断直接确认） |

E2E-06 的失败不可能是该 panic 造成的：`signal` 服务器上的目的地只在 07a/07b/07e 里设置，而按文件顺序 E2E-06 在它们之前运行，进入该用例时该服务器从未收到过目的地请求，退化路线无从产生。E2E-07b 同理——它的 `waitGlosa` 在 5.5 s 内就返回了，说明帧流当时仍在推进。

## 2.1 产品侧缺陷：空 edges 路线在 §40 限速提醒分支越界索引

这一项不在原计划内，是把 §10 要求的 server stderr 诊断接上之后**立刻**显形出来的，因此按发现顺序如实记录。

首个 PR 运行（run [34699834330](https://github.com/HaowenCang/ETS2Nav/actions/runs/34699834330) @ `68aa944`）在刚恢复为硬门的 `Browser loopback security` 上失败，失败信息里直接带着根因：

```text
合法请求必须把**持久会话目的地**设为 A（尝试 4 次）。
诊断：{"http":{"a":[200,200,200,200],...},"snapshot":{"baseline":{"status":200,"pos":null}},
      "observer":{"frames":5,"vehicles":4,"mapStates":[[-58456,32832]]},...,
      "serverStderrTail":"…[server] 目的地已设置 (-58456,32832)
        thread '<unnamed>' (5076) panicked at crates\nav-router\src\session.rs:454:66:
        index out of bounds: the len is 0 but the index is 0"}
```

`session.rs` 的 §40「前方限速变化」提醒分支直接索引 `route.edges[0]` 取 road_class，而 `speed::speed_breaks_ahead` 在「`route.edges` 为空、但存在虚拟段」时仍会产生断点——它的入口只在 edges 与两个虚拟段**全空**时才返回空。该形态完全可达：起终点吸附到不同边、而 astar 未产出任何图边时，`search.rs::single_edge_route` 给出的正是 `edges: []` 加两个虚拟段。

BLS-01 恰好命中：它把目的地 A 设为合成 trace 的起点 `(-58456,32832)`，而 BLS 自己的服务器在 `beforeAll` 里刚启动、车辆正位于 trace 起点附近，「从当前位置到 A」因而是一条退化路线。是否 panic 取决于两个虚拟段落在限速相同还是不同的边上——相同则只有一个 offset 0 的断点，`find(|b| b.offset_m > traveled + 0.5)` 不成立，分支根本不进入；不同则在 offset>0 处多出一个断点。这解释了它的偶发性，也解释了为何同一 SHA（`98d199b`）上的两次运行给出相反结论。

后果远大于少一条提醒：panic 发生在服务端的**数据源线程**内，该线程终止后服务端完全停止广播（上例中 `vehicles` 停在 4）。测试侧只能看到「目的地设了但持久状态一直不变」，而 Batch 5 的观测手段无法把这一情形与「观测通道没收到」区分开——两者方向相反，却给出同一条失败信息。这正是 §8 要求分层证据的直接理由，也是 §10 要求补 server stderr 的直接收益。

修复取首段所在边的顺序为 `edges[0]` → `start_virtual` → `end_virtual`，全为空时跳过该提醒。顺序保持既有语义不变：正常路线仍取 `edges[0]`，因此这不是行为变更，而是补上 session 内唯一未设防的路线边索引。`maneuver.rs` 与 `tracker.rs` 的对应访问已逐一核对，各自都已处理空 edges 形态（`generate_maneuvers` 有专门的单段分支，`edge_remaining` / `time_remaining` / `distance_to_edge` 都以 `is_empty` 提前返回）。

回归测试 `session::tests::empty_edges_route_does_not_panic_in_speed_limit_reminder` 用两条平行且限速不同的边构造该形态，并先断言「确实存在 offset>0 的断点」——否则用例到不了被修复的那一行，会退化成一个永远通过的空断言。反向验证：把该处改回 `Some(route.edges[0])` 后用例 exit 101，恢复后 exit 0。

需要明确的是，这条修复消除的是一个**已知的具体 panic**，不是让服务端对 panic 免疫。数据源线程内任何其它 panic 仍会终止广播；本轮的处置是让这种终止在测试里**可见并分类**（§6 的 `assertServerAlive`、§8 的 `serverPanicked`），而不是继续表现为超时。

## 3. E2E-07b 的 TOCTOU 判别实验

修改代码之前先做判别实验，把"旧形态可以返回与判定不一致的值"从推断变成可重复的事实。用例是 `tools/ets2nav-web/tests/e2e/14-glosa-helper-race.spec.mjs`（E2E-07f），同时作为回归门保留。

构造方式刻意做成确定性而非靠时序碰运气。做法是在页面里包一层 `document.getElementById`：谓词读取 `#glosa` 时，在**当前宏任务末尾**（`setTimeout(…, 0)`）把文本清空。这与 app.js 的真实行为同构（帧 N 写入区间、帧 N+1 清空），并给出两个必然结果：谓词这一次求值必然看到合法区间（同步代码不会被翻转抢占），此后任何一次新的浏览器往返必然看到空串。

```text
旧形态（waitForFunction + locator.textContent）→ 返回 ""，parseGlosa 返回 null
新形态（waitForFunction 返回匹配值本身）      → 返回 "建议 15–40 km/h"，parseGlosa 返回 {15,40}
```

实验过程中有一处否证值得记录，它改变了构造方式。第一版把 `textContent` 作为元素自有访问器来计数读取次数，结果得到"只读了一次"的假象：`page.evaluate` 与 `page.waitForFunction` 共享主世界（能看到自有访问器），而 `locator.textContent()` 的元素包装来自另一个 realm，看不到它。若沿用该构造，实验会得出"旧形态没有二次读取"的错误结论。最终构造把判别点放在**只被谓词调用**的 `document.getElementById` 上，定位器侧走选择器引擎，两侧因此天然分离。

该用例同时是回归门：若有人把 `waitGlosa` 改回两次往返，它的后半段会失败。这是 §13 的 M1 之外对 helper 自身的直接防护。

## 4. `waitGlosa` 修复

判定与取值合并到同一次 browser-context evaluation 内完成：谓词不再返回布尔值，而是返回**匹配到的字符串本身**；`waitForFunction` 解出时携带的就是那次判定的取值快照（Playwright 对返回真值的求值结果取 JSHandle），此后不再读 DOM。

```js
const handle = await page.waitForFunction((m) => {
  const t = document.getElementById("glosa").textContent;
  const ok = /* mode 判定 */;
  return ok ? { matched: t } : false;
}, mode, { timeout });
return String((await handle.jsonValue()).matched).trim();
```

返回值用 `{ matched }` 包一层而不是直接返回字符串，原因是 `mode === "empty"` 的合法结果就是空串，而 `waitForFunction` 以真值作为"已满足"判据——直接返回空串会被当成未满足而永远等下去。

没有采用的处置，以及为什么：加 `sleep`、加 retry、把 30 s 改 60 s、放宽 `parseGlosa`。四者都只改变失败概率或改变判据，而这里的问题不是"没等到"，把窗口拉长对"取回来的值已经变了"没有任何作用。`E2E-07b` 现在额外断言 `waitGlosa(range)` 的**返回值本身**满足 `/^建议 \d+–\d+ km\/h$/`，使该 helper 的契约被直接锁定，而不是只由下游的 `parseGlosa` 间接体现。

## 5. fake-signal 相位与 E2E-06 时序分析

剧本按帧号推进，六阶段循环，每阶段 40 帧（`nav-router::session`）：

```text
frame:  0        40       80       120      160      200      240
phase:  0 Red    1 Red    2 Yellow 3 None   4 Green  5 Red    0 Red ...
```

`E2E-06` 原来的等待顺序是 Red → Green → Yellow，与上述序列不一致。从任意进入相位出发所需跨越的阶段数：

| 进入相位 | 等到 Red | 再到 Green | 再到 Yellow | 合计阶段 |
| --- | --- | --- | --- | --- |
| 2（Yellow，最坏） | 3（2→3→4→5） | 5（5→0→1→2→3→4） | 4（4→5→0→1→2） | 12 |

单看最坏一次等待是 5 个阶段；整段顺序等待的最坏情形是 12 个阶段，即 480 帧。而 `Yellow` 与 `Green` 各自只驻留 2 s，每一步之后的 `toBeVisible()` / `toHaveClass()` / `toHaveText()` 又各是一次独立的浏览器往返——判定与断言分处两个时刻，正是"Test timeout of 60000ms exceeded"落在 `waitForFunction` 内部的形态。

帧节奏的实测值（`C:\Temp` 探针，认证 WS 计数，30 s 窗口）：

```text
frames=578 elapsedMs=30009 perFrameMs=51.92 fps=19.26
  Red     120 frames  6222 ms  51.85 ms/frame
  Yellow   40 frames  2063 ms  51.58 ms/frame
  None     40 frames  2060 ms  51.50 ms/frame
  Green    40 frames  2067 ms  51.67 ms/frame
一个完整周期 = 240 帧 ≈ 12.5 s
```

节奏由服务端自定：`--replay` 每帧 `sleep(sim_time_delta.min(200ms))`，而合成 trace 的 `simulation_time` 每帧推进 50 000 µs，故标称 50 ms/帧；实测 51.9 ms 是加了每帧处理开销后的值。这个方向性是关键：**服务端的帧间隔只可能被拖长、不可能被缩短**，因此慢 runner 会让每个阶段变长，不会让某个阶段被跳过。相位覆盖的正确计量单位因此是帧数，而不是秒数。

这也解释了 `E2E-06` 的 31.7 s（远端绿色运行）：它由进入相位决定，是在 0–24 s 的纯等待上叠加页面建立与断言往返的结果，是一个**跨周期长尾**而不是稳定耗时。

## 6. E2E-06 稳定化设计

采用 §4 的**方案 A（observation-set）**，理由是它同时满足两条硬约束：保留 `fake-signal → NavigationSession → snapshot_json → WebSocket → app.js → DOM` 这一整条真实链路，同时使完成条件与进入相位、runner 快慢都无关。

采样点选在 app.js 顶层的 `dispatchMessage`：`ws.onmessage` 的实现是 `dispatchMessage(ev.data)`，即调用时才解析全局名，因此包住全局函数即可在**每一帧真实到达 WS 之后、原函数返回的同一同步块内**采集该帧产生的 DOM 契约。链路完全不变，被覆盖的只有"读"这一步。每个样本记录 `state / hidden / cls / remaining / glosa / session`。

完成条件：

```text
所需状态全部出现   或   已采集帧数达到 240（= 一个完整剧本周期）
```

240 的推导是结构性的而不是经验性的：所需 DOM 状态对应阶段 Red ∈ {0,1,5}、Yellow = 2、None = 3、Green = 4，从任意相位出发的最坏情形是"刚错过 Red 块"——此时需依次经过 2、3、4、5 才重新看到红，共 5 个阶段 200 帧；取一个完整周期 240 帧作为上界，留 40 帧余量，而上界本身仍由剧本结构确定。墙上超时只作为"帧流已死"的兜底，不承担相位对齐职责。

断言强度比原实现更高：原来只检查"有一次相符"，现在对采集到的**每一个**样本逐条核对（Red/Yellow/Green 三态都要求卡片可见、class 等于灯态本身、剩余时间匹配 `^剩余 \d+\.\ds$`；无信号态要求卡片隐藏且 state/remaining 文本被清空）。

没有采用方案 B（扩展测试钩子以显式控制相位）：它需要给 session 增加一个跨线程可写的相位覆盖状态，并在服务端开放一个控制接口；`fake_signal=false` 的生产路径虽可保持不变，但这会为测试引入一处新的、必须靠约定来保证"只在 test mode 存在"的认证面。方案 A 在不触碰产品代码的前提下达到了同样的确定性，因此没有必要承担这份风险。也没有采用方案 C：方案 A 已经把 DOM 契约建立在真实链路上，再拆一份 `deliverFrame` 覆盖会重复而非增强。真实链路的保留由 E2E-07a/07b/07e 继续承担（§7）。

窗口完成之后还必须通过 `assertServerAlive`（§10）：数据源线程一旦 panic，帧流会静默停止，上面这条帧证据等待只会表现为超时，而产品崩溃与测试同步问题必须分开报告——这是 §2.1 那次失败给出的直接教训。

## 7. E2E-07 的 phase coupling 审计

审计对象是 07a / 07b / 07e 是否因共用同一个长期运行的 signal 服务器而产生隐含的 wall-time coupling。确实存在，而且不止一种。

第一层是**相位耦合**：三个用例进入时所处的剧本相位取决于浏览器启动耗时与之前全部用例的累计耗时。处置与 §6 同源——窗设计为按帧计量。

第二层更隐蔽，是本轮审计的主要收获：**会话状态耦合**。§38 只在 `if self.state == SessionState::Navigating` 分支内计算，而两件事会让会话离开该状态，且都取决于用例开始时车辆处于 trace 的哪一段：

```text
server_cli.rs 回放循环每轮结束：session = NavigationSession::new(...)
  → 目的地随之丢失，会话回到 Idle，§38 停止计算（A2c-M3 的重建是有意的：
    不重建则首轮 Arrived 之后永久卡死）
车辆驶到 trace 终点附近（约 6 min 周期）→ Arrived
```

原始实现对此没有防护，其结论因此部分依赖"车辆恰好在 cycle 的哪一段"。处置是让测试自己维持它声明的前置条件：采集循环发现会话掉出 `NAVIGATING` 时，经**真实 UI 路径**（填坐标 + 点按钮）重新设目的地。这不是绕过产品链路，而是把"会话正在导航到 X"这一前提显式化。

第三层是 07e 自身的一个真实竞态。原实现"等到绿灯后再采样 1.5 s"，而绿灯只驻留 2 s：若等待在绿灯末尾解出，采样窗内可能一个绿灯样本都没有，`duringGreen.length > 0` 直接失败。现改为在同一份帧证据里取绿灯样本，并把**非空前提写进完成条件**（要求 ≥20 帧绿灯样本，半个阶段），而不是事后检查。

07e 还补了一条**正向对照**：窗口内必须出现至少一帧带区间的红灯样本。缺少它时，"绿灯期间 GLOSA 为空"在 GLOSA 整体失效的情况下会假通过——这正是原实现的形态。

红灯区间的取值与车速无关，这一点经过源码核实而非推断：三个红灯阶段的可达上限分别由 `d/t1`（120/12=36 km/h、100/5.6=64 km/h、60/18=12 km/h）与限速 cap 决定，而可达加速度上限 `sqrt(v² + 2·a·d)` 在所有阶段都大于它们（最小者 `sqrt(2·2·60)=15.5 m/s=55.8 km/h` 也大于 12 km/h），故 `v_hi` 与车速无关，区间恒为 15–40 / 15–65 / 5–15。E2E-07a 因此可以对**每一个**导航中红灯样本断言区间形态，而不只是"某一次"。

## 8. BLS-01 oracle 分层

先重新定义被测的安全性质：**跨源、无 token、`text/plain` simple POST 不得改变 navigation destination**。这是一个关于**持久会话状态**的命题，不是关于某次广播的命题。

按 §7 的要求先核查 `GET /api/snapshot` 能否充当权威 oracle。结论是**原来不能**：该端点的 `destination` 字段是 `NavigationSnapshot.destination`，其来源是

```rust
destination: self.destination.as_ref().map(|d| d.name.clone()),
```

即目的地的**显示名**，而 `/api/route` 为坐标目的地一律填 `"目标"`，A/B/C 三者取不到区分度。用它当 oracle 等于什么都没断言。

因此为 §60 vehicle 帧增加了 `destination_pos`（与显示名同源同帧，来自 `NavigationSession.destination.position`，新增 Rust 契约测试锁定"字段恒存在、无目的地为 null"）。`/api/snapshot` 返回的正是数据源线程每帧写入的 `latest_json`，而该帧的 `destination_pos` 直接来自 session 的持久字段——它不是对最近一次 HTTP 请求的回显（HTTP 处理路径明确只写 `pending_dest`，注释记载 `latest_json 保持 vehicle 语义`）。

BLS-01 的新结构：

1. 建立已认证 WS observer，保留为次证据与诊断；
2. 合法设定 A → `POST /api/route` 200，并轮询持久状态直到 `destination_pos == A`；
3. 发跨源攻击 B，在一个**有语义的观察窗口**内连续采样持久状态，确认 B 一次都没有出现；同时确认攻击请求确实发出、服务端确实拒绝（浏览器侧捕获 401）、并且 `map_state` 广播里也没有 B；
4. 合法设定 C → 200，持久状态必须最终为 C，证明产品 route 路径仍然活着；
5. WS observer 若看见 C 是第二证据；**若持久状态为 C 而通道未见 C，记为 `WS BROADCAST OBSERVATION GAP` 并打印诊断，不判安全性质失败**。

观察窗口的长度由副作用路径本身确定，而不是猜：被接受的 `POST /api/route` 只把目标写进 `pending_dest` 单槽邮箱，由数据源线程**每帧消费一次**，故最迟 1 帧（标称 50 ms）生效；6 s ≈ 120 个标称帧周期。窗口内同时要求 ≥20 次快照采样成功，使"窗口过去了但 oracle 没被真正使用"无法伪装成通过。

BLS-02 采用同一分层（负向判据同样改为持久状态，正向对照同样以持久状态确认）。

**这不是削弱断言。** 安全副作用 oracle 本来就应当看持久状态；WS 事件投递由 BLS-03..09 与协议套件专门覆盖。原实现把一次非核心的瞬时事件当作唯一真值来源，其后果是把"广播没收到"记成"安全回归"，方向恰好相反。`waitDest`（等待目的地出现在广播中）因此被移除，并留下注释说明它为何被移除——不是因为它太严格，而是因为它测错了对象。`near()` 的 1 m 判据、401/403 断言、opaque 响应断言、预检断言全部保留。

## 9. snapshot 与 WS 的分歧分类

按 §8 要求，两种分歧必须给出方向相反的分类，且在报告与诊断里不能混写：

```text
HTTP 200 且 snapshot destination_pos == C，但 WS observer 没有收到 C 的 map_state
  → WS BROADCAST OBSERVATION GAP
    这是观测通道的问题，由 BLS-03..09 与 test:protocol 决定是否 FAIL。
    BLS-01 记录并打印，不判安全失败。

HTTP 200 但 snapshot destination_pos 始终不是 C
  → PRODUCT / SESSION PROCESSING FAILURE
    这是产品侧问题：请求被接受但没有进入 session。必须停止并调查。
```

第二种情形在本轮的 mutation 验证中被真实构造出来（§11 的 M4），失败信息为：

```text
合法请求必须把**持久会话目的地**设为 A（尝试 4 次）。
诊断：{"http":{"a":[200,200,200,200],...},"snapshot":{"baseline":{"status":200,"pos":null}},
      "observer":{"frames":632,"vehicles":632,"mapStates":[]}, ...}
```

四次要约 200 而未生效，`mapStates` 为空数组——这组证据把"请求被拒"与"请求被接受但未生效"分开了，而后者在原设计下只会表现为一句"正向对照必须成功"。

## 10. 失败诊断

E2E-06/07 侧新增 `dumpUiState(page, port)`，一次性取回：`signal-state` 文本与 class、`signal-card` 可见性与 class、`signal-remaining`、`glosa`、`state-chip`、`conn-status`、`ws.readyState`、已采样帧数、最近 12 个样本，以及**该服务器实例的 stderr 尾部**。E2E-06 与 07a/07b/07e 的所有失败信息都附带该诊断。

server stderr 是 E2E-06/07 侧此前缺失的一环，补它的收益不是理论上的：同一个 panic 在 BLS 侧因为有 stderr 而被一眼定位（§2.1），在 E2E-06/07 侧则只会表现为「等待状态推进超时」。实现上必须落盘——服务器进程由 globalSetup 在 Playwright 的 runner 进程中建立，spec 运行在 worker 子进程里，拿不到进程句柄，因此 `harness.mjs` 把 stderr 同时写入 `SESSION_DIR/server-<port>.err.log`，`helpers.mjs` 的 `serverStderrTail` 再读回尾部。

仅把 stderr 放进失败信息还不够：那样只在已经失败之后才有用，而且会把「服务端崩了」继续记成「等超时了」。因此新增 `assertServerAlive(port, label)` 并放在**成功路径**上——E2E-06 与 E2E-07a/07b/07e 在帧证据窗口完成之后都必须通过它。这样产品崩溃会在失败信息中显示为崩溃本身（附 `panicked at` 原文），而不是伪装成同步问题。

BLS 侧在 Batch 5 已加的 `closed` / `errored` / `frames` / `vehicles` / `mapStates` 之上补齐：observer `readyState`、A/B/C 的 HTTP 状态（含攻击请求的 opaque 响应与浏览器捕获的响应码）、攻击前后的 snapshot 目的地、正向对照后的 snapshot 目的地、`serverPanicked` 布尔字段与 server stderr tail。

令牌处理是硬要求而非美化：诊断经过 `redact()`，把 64 位十六进制串替换为 `<token-已遮蔽>`、把 `token=` 参数值替换为 `<已遮蔽>`。会话令牌从不进入任何被打印的文本，`/ws?token=...` 形态的完整 URL 不会被写出。

## 16. Security Portable 的最终语义

`Security Portable` 现在真实门控两条：`Server protocol integration`（`npm run test:protocol`）与 `Browser loopback security`（`npm run test:browser-loopback`，BLS-01..09，真实 Chromium + 真实攻击页面）。后者已从 Batch 5 的 `continue-on-error: true` 恢复为**普通门控步骤**，job 内不再有任何针对它的例外机制。

恢复的依据不是"重跑变绿"，而是判定对象的变化：BLS-01/BLS-02 的副作用判据由瞬时广播改为持久会话状态（§8），"广播没收到 ⇒ 判安全失败"这条伪失败路径因此不再存在。除 LAN 矩阵外，工作流中已无 `continue-on-error`；`Web E2E` 与 `Browser loopback security` 都不使用它。

`Security Portable` 通过因此只声称 **portable protocol + browser-loopback**。它**不**声称完整 S1–S11 局域网矩阵已在云端通过，这一点由 job 名与本文档共同承载；只读 job 名不足以推出该限制，因此 README 中也写明了同一句。

## 17. LAN 完整矩阵的限制

完整 S1–S11 在本机可执行且全部有结论：`FAIL=0 NOT_VERIFIED=0 SKIP=0`、`LAN SECURITY: PASS`，其中 S9 依赖本机 VPN 隧道地址 `198.18.0.1`（非 RFC1918、可连接），使 `Disallowed` 对端类别可以被真实构造。hosted runner 不具备这样的地址，S9 因此报 `NOT VERIFIED` 并以非零退出，脚本仍然原样运行、原样报告，工作流中该步骤仍是 `continue-on-error` 的信息性步骤。

本轮**没有**再次尝试改 runner 网络。Batch 5 曾按方案 1 给 runner 网卡注入 RFC 5737 文档用地址，该步骤在 runner 上超过 6 分钟未返回、取不到输出且不响应取消，并因占住并发组而使后续运行停在 pending；该现象至今未定位到具体阻塞点。这是环境能力边界，不是仓库缺陷，本轮按 §11 明确不要求关闭它。

需要与上表一起读的推论：`Security Portable = PASS` 与 `LAN full security matrix = PARTIAL` 同时成立并不矛盾，前者是 required check 的实际覆盖，后者是本地/发布门的覆盖。把两者混写会让读者以为云端已覆盖完整局域网攻击面。

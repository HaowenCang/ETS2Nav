### 2.2 判定缺陷的四种具体形态

**管道吞掉退出码。** CMD 的 `a | b` 令 `ERRORLEVEL` 取 `b` 的退出码。`cargo test 2>&1 | findstr /C:"FAILED"` 于是把「测试通过」判成「findstr 没找到 FAILED」。两个方向的掩盖都真实存在：`cargo test` 若因**编译错误**失败，输出是 `error[E0599]` 而**不含** `FAILED`，findstr 找不到即判 `CARGO TEST PASS`——编译不过被报告为测试通过。P5 的 `od-corpus` 步骤搜索了 `"error[E"`，P2/P3 的 `cargo test` 步骤没有，同一类缺陷只在其中一处被部分规避。

**反向判定。** P5 的 `if errorlevel 1 (echo CARGO TEST PASS)`：`findstr` 退出码 1 表示「没找到」却被当作成功条件。当 `cargo` 本身无法启动（PATH 缺失、crate 名写错）时输出为空，findstr 找不到任何东西 ⇒ PASS。

**恒真 marker。** `nav-core-cli match` 的统计行 `匹配: HIGH n / ...` 无条件打印，`findstr /C:"HIGH"` 因此即使 `HIGH=0` 也匹配；`nav-core-cli signal` 的成功分支打印「共 N 个受控 movement」、失败分支打印「路线中无受控 movement」——两者都含 `movement`，`findstr` 无从区分。

**自证式 baseline。** P5 在基准缺失时先生成、再与刚生成的文件比较，这在结构上不可能失败。

## 3. 新 harness 架构

判定逻辑集中在一处：`scripts/regression.ps1`（唯一 oracle）。四个 `.bat` 退化为薄包装——只做编码前置检查、转发参数、原样传播退出码，不含任何测试判定。

```
scripts/regression.ps1                 唯一判定实现（-Suite P1|P2|P3|P5|All|SelfTest）
scripts/harness-encoding-guard.bat     编码前置条件（.ps1 必须 UTF-8 with BOM）
scripts/harness-fixtures/              H1/H2/H5 夹具（不触碰产品代码）
scripts/verify-clean-clone.ps1         clean-clone 复现验证
run-p1-tests.bat … run-p5-tests.bat    薄包装（历史入口保持不变）
```

套件链与历史一致：P2 链内含 P1，P3 链内含 P2。同一次调用内已执行过的链标记为 `reused` 并沿用首次执行的真实退出码，因此 `-Suite All` 不会把 P1 跑三遍，而 `run-p2-tests.bat` 单独调用时仍是自包含的完整链。日志形如：

```
[P2:chain-p1] PASS (chain P1, steps=15, failed=0, reused)
```

### 3.1 判定契约

```
PASS  ==  (进程退出码 ∈ AcceptExitCodes)  AND  (语义断言为真)
FAIL  ==  其他情况
```

退出码是主判据：`exit != 0` 时无论 stdout 出现什么（包括 `PASS`、`ALL TESTS PASSED`）一律 FAIL（H1 实测）。语义断言只做加法：某步骤声明了语义断言时，`exit == 0` 但 marker 缺失同样 FAIL（H2 实测）。文本断言不再是判定的唯一依据，也不再存在「找不到 FAILED ⇒ 成功」的推理。

### 3.2 退出码语义

| 码 | 含义 | 触发条件 |
| --- | --- | --- |
| 0 | PASS | 全部步骤 PASS |
| 1 | TEST FAILURE | 某个步骤的被测命令或语义断言不满足 |
| 3 | PRECONDITION FAILURE | 外部输入缺失/不可用（环境问题，不是产品缺陷） |
| 4 | HARNESS FAILURE | harness 无法可信执行：参数误用、构建产物缺失或陈旧、执行了仓库外文件 |

§15 要求的三类区分由此成为机器语义。本轮实测三种都出现过：案例 1/2/3 为 3，`cargo-fmt` 步骤为 1（§16.2），闭包计算缺陷为 4（§17.4）。

| 解包根 | `-Ets2Extracted` | `ETS2NAV_EXTRACTED` | `vendor/extracted` | P1（`dotnet test` 内的集成测试同约定） |

| OD 基准 | `-OdBaseline` | `ETS2NAV_OD_BASELINE` | `od-baseline-europe-v5.txt` | P5 |
| trace | `-Trace` | — | 本轮临时工作区现场生成 | P2 |

两条附加规则使「路径写错」不会被静默掩盖：

- **显式参数或环境变量指向不存在的路径时立即 PRECONDITION FAIL，不回落到默认值**。若允许回落，`-Dataset D:\typo` 会静默测到 `data/europe-v5`，正是本批次要消除的掩盖。案例 1 实测：`-Dataset "<不存在>"` → exit 3、0.4 s、未启动任何步骤。
- **解析后的输入导出为子进程环境变量**（`ETS2_INSTALL`/`ETS2NAV_EXTRACTED`/`ETS2NAV_DATASET`/`ETS2NAV_OD_BASELINE`），使 `dotnet test` 内部的测试与 harness 看到同一组输入，不会出现「参数传一个、环境变量里是另一个」。

不得猜测用户磁盘位置：本机游戏路径不出现在仓库任何被跟踪文件中（§17.2 为全仓扫描结果）。

## 5. exit-code oracle 设计

`Invoke-NativeStep` 是唯一执行器，输入 `name / executable / arguments / workingDirectory / 语义谓词 / AcceptExitCodes`，输出 `ExitCode / Stdout / Stderr / SemanticPassed / Duration / Result`。

**不使用 `$LASTEXITCODE`，也不使用管道。** 实现基于 `System.Diagnostics.Process`：`ExitCode` 直接取自进程对象，stdout/stderr 通过 `Stream.CopyToAsync` 以**原始字节**读出后再解码。§19 关注的「读 `$LASTEXITCODE` 之前又执行了别的 native 命令」「capture 方法丢掉退出码」两类风险在设计上不存在。

输出解码按 UTF-8 严格解码（`UTF8Encoding(false, true)`，非法字节抛异常），失败则回退到本机 OEM 代码页。这是必要的：Rust 工具恒定输出 UTF-8，而 .NET 控制台在重定向时使用控制台代码页（本机 zh-CN 下为 936）。每条步骤的 meta 日志记录实际使用的解码器，可复核。

实测中一个反例说明了管道纪律的必要性：用 `& exe … | Select-Object -First 4` 读取 `nav-core-cli speed` 的输出时，`-First` 提前终止管道并杀死上游进程，`$LASTEXITCODE` 变成 `-1`（进程被终止）而非真实值。harness 的实现不做此类流式截断——输出先完整落盘，再取尾部。

Windows 命令行参数的引号规则按 `CommandLineToArgvW` 语义自行实现（反斜杠在引号前的加倍、内嵌引号的转义），并有 8 例单元断言（H5）。

已知边界：`Invoke-NativeStep` 不做 `cmd.exe /c` 特有的去引号补偿（`cmd /c "<带空格路径>" …` 会剥掉外层引号并在空格处断开）。这不是 `ProcessStartInfo` 的行为，而是 cmd 自身的解析规则，且本 harness 的全部真实步骤都直接执行 exe，不经过 cmd。H5 因此用 `powershell.exe -File` 夹具验证引号层。

## 6. semantic assertion 设计

语义断言一律是**正向**断言（存在某结论行、某计数 ≥ 阈值、某正则匹配），因为这些断言在文件编码或输出格式意外变化时会失败而不是静默通过。逐步清单：

| 套件 | 步骤 | 断言 |
| --- | --- | --- |
| P1 | `dotnet-test` | exit 0 且含 `Passed!` 与 `Failed: 0`（防止「0 个测试被跑」被当作成功；`DOTNET_CLI_UI_LANGUAGE=en` 由 harness 设定以保证 marker 与语言环境无关） |
| P1 | `build-map-inspector` / `build-dataset-reader` | exit 0，且产物存在、非空、不早于其依赖闭包中的任何源码 |
| P1 | `gate-berlin` / `gate-germany` | exit 0 且含 `GATE 通过` |
| P1 | `det-build-1` / `det-build-2` | exit 0 且四个产物（`routing.graph`/`junction.graph`/`map.db`/`search.db`）存在且非空 |
| P1 | `determinism` | 两次独立构建的四个产物 SHA-256 全等（harness 内比对，无进程） |
| P1 | `europe-scale` | exit 0 且含 `diagnostics.json 已写` 与 `已加载 N 个 sector` |
| P1 | `europe-diagnostics` | `diagnostics.json` 含 `failed_prefabs` 键且计数为 0（缺键也 FAIL，不再依赖 KeyError 崩溃来判失败） |
| P2 | `cargo-fmt` / `cargo-clippy` | exit 0（clippy 用 `-- -D warnings`，使警告成为错误；原实现只搜 "warning" 字样且 clippy 退出码恒 0） |
| P2 | `cargo-test` | exit 0 且至少一个 `test result: ok.` 且无 `test result: FAILED`（编译错误会被退出码捕获，不再落入「找不到 FAILED」） |
| P2 | `syntrace` | exit 0 且含 `SYNTRACE OK` |
| P2 | `trace-freshness` | trace 位于本轮临时工作区内、名为 `synthetic.navtrace`、非空 |
| P2 | `route-regression` | exit 0 且含 `P2-18 Regression PASS` 与 `不一致 0`（后者是新增的第二层：原实现只在 tracker/maneuver 上断言，profile 间不一致数并不参与判定） |
| P2 | `match-replay` | exit 0 且 `匹配: HIGH N` 中 `N ≥ 1`（原 `findstr HIGH` 在 `HIGH 0` 时同样匹配） |
| P2 | `signal-link` | exit 0 且 `共 N 个受控 movement` 中 `N ≥ 1`（该行只出现在成功分支；「无受控 movement」不再算通过） |
| P2 | `perf-smoke` | exit 0 且同时含 `Bench PASS`、路线统计行、匹配统计行、`[限速查询] 10000 次`、进程工作集统计行 |
| P3 | `speed-lookahead` | exit 0 且含数据集金值 `breaks=2 (machine-readable)` |
| P3 | `camera-verdict` | exit 0 且 `VERDICT` 行恰好出现一次且值为 `NO-GO (machine-readable)` |
| P5 | `cargo-test-od-corpus` / `cargo-test-nav-router` | exit 0 且至少一个 `test result: ok.` |
| P5 | `od-regress` | exit 0 且含 `OD-REGRESS PASS` 与 `diff=0` |
| P5 | `od-check` | exit 0 且含 `OD-CHECK PASS` |

**刻意不做的一件事**：`bench` 的墙钟阈值（路线 p99<500 ms、匹配 p99<10 ms、限速查询 p99<10 µs）**不**写成判定门。把墙钟阈值写成门会引入依赖机器的概率判定，与本批次消除概率测试的目标相反。阈值仍由 `bench` 自身打印，供人工与报告核对；报告 §16 记录了本轮实测值。

**CameraProbe 的 contract（§11 专项）**：`VERDICT=NO-GO` 是该工具的**预期成功结论**（含义为「欧洲 sector 的 prefab/model/sign token 中没有任何测速摄像头编码，故无法提供摄像头限速」），不是错误。工具自身没有 `Environment.Exit`，其退出码表达的是**执行成功/失败**（异常则非 0）。原判定 `dotnet run … | findstr "VERDICT=NO-GO"` 存在「程序在打印 VERDICT 之后崩溃仍判 PASS」的可能——VERDICT 行在源文件第 145 行打印，其后仍有两条输出语句。新判定要求 `exit == 0` **且** VERDICT 行唯一且值精确匹配，两个条件缺一不可。

## 7. P5 baseline policy

**基准是回归 oracle，不是测试产物。** 规则：

- 普通回归模式下基准必须存在，缺失即 PRECONDITION FAIL（exit 3），**永不自动生成**。原实现在缺失时生成再与自身比较，该路径已彻底移除。
- 更新基准是独立的显式维护动作：`scripts/regression.ps1 -Suite P5 -UpdateBaseline`（`run-p5-tests.bat` 不暴露它）。该模式拒绝与 `-Suite All` 组合，打印醒目声明「这是审查动作，不是测试」「生成后与自身比较必然一致，因此『通过』在这里没有验证意义」，覆盖已存在的基准还需额外 `-Force`。
- 生成采用「先写候选文件 → 打印与现有基准的差异摘要 → 再落盘」，落盘后用 `LastWriteTime = Now` 修正 mtime（`Copy-Item` 会保留源文件 mtime，Batch 3 已因此吃过陈旧产物的亏）。
- 基准文件 `od-baseline-europe-v5.txt` **已纳入版本控制**（36 对，1701 B）。§6 的优先选项即「体积合理且本质是 oracle ⇒ 版本化」，该文件已满足，无需外置。

实测（§12）：缺失基准 → exit 3 且**未创建文件**；已存在基准 + `-UpdateBaseline` 无 `-Force` → exit 3 拒绝覆盖；`-Force` 指定临时目标 → exit 0，写入的候选文件与被跟踪基准**逐字节相同**（SHA-256 前缀 `C32BAD5F2C407C44`），被跟踪基准哈希前后未变。最后一项同时是基准生成确定性的一次独立证据。

## 8. synthetic trace policy

每轮在唯一临时工作区 `%TEMP%\ets2nav-regression-<时间戳>-<pid>-<随机>\` 内现场生成 `synthetic.navtrace`，运行结束时删除；失败时保留并打印完整路径与步骤日志目录。旧的 `%TEMP%\real.navtrace` 复用逻辑（存在即用、不清理、跨轮跨用户同名污染）已移除，名称本身也改掉——它从来不是真实采集数据，叫 `real` 只会误导。

`bench` 的 trace 改为显式输入（`--trace=<path>` 或 `ETS2NAV_TRACE`），缺失时打印明确的 `[匹配] 跳过（未提供 trace…）` 行并以 0 退出（跳过不是失败），而传入的路径不存在时以 1 退出。四种组合实测见 §16。

## 9. stale binary 处理

**每一个被执行的二进制都在本轮显式构建。** P1 构建 `map-inspector`（不在 `MapCompiler.sln` 内）与 `dataset-reader-smoke`（不在 nav-core workspace 内）；P2 构建 `dataset-reader-smoke` 与 `nav-core-cli`；P5 构建 `od-corpus`。不再存在「按需才构建」的分支。

构建之后追加**产物新鲜度断言**：产物必须存在、非空，且 mtime 不早于其**依赖闭包**内任何源文件（宽限 2 s，吸收文件系统时间戳粒度）。依赖闭包是精确计算的：

- Rust：`cargo metadata --format-version 1 --locked` 求包的可达依赖子图，只取仓库内的路径依赖（注册表依赖的 manifest 在仓库外，排除）。实测 `od-corpus` 与 `nav-core-cli` 的闭包各为 7 个目录，且**互不包含对方的包目录**。
- C#：从 csproj 递归收集 `ProjectReference`。

精确性是被实测逼出来的：最初用整个 `nav-core` 当比较根，结果编辑 `nav-core-cli/src/main.rs` 后 `od-corpus.exe` 被判为「陈旧」——而 `od-corpus` 根本不依赖 `nav-core-cli`。那是**假 HARNESS FAILURE**（exit 4），与漏报同样有害。改用依赖闭包后该误报消失（§17.4）。

新鲜度断言的实际价值在于捕获 Batch 3 的教训：源码被恢复但 `Copy-Item` 之类的操作把 mtime 回退，构建系统可能继续复用变异后的二进制。`Touch` + 重新构建是必要步骤，哈希与 mtime 是它的复核。H4 则验证「产物被删除后必须自动重建，而不是 file-not-found」。

## 13. E2E-09 根因

**这是产品缺陷，不是测试缺陷。** 机理（实测，非推断）：

`onSnapshot` 每 50 ms（20 Hz 快照）调用一次 `map.easeTo(...)`。MapLibre 的 `Map.easeTo()` 第一条语句是 `this._stop(false, options.easeId)`；`allowGestures === false` 会走到 `handlers.stop()` → `HandlerManager.stop()`，它对**所有**交互 handler 调用 `reset()`，其中 `DragHandler.reset()` 删除 `_lastPoint`，此后 `dragMove()` 因 `if (!lastPoint) return;` 永久提前返回。于是存在一个致命窗口：`mousedown` 之后、位移首次超过 `clickTolerance` 的 `mousemove` 之前，只要有一次 `easeTo` 落下，这次拖动就永久失效——MapLibre 不再发 `dragstart`，改在 `mouseup` 时发 `click`，挂在 `dragstart` 上的 `pauseFollow` 从不执行，相机继续跟随。

判别实验（每条件 16 次，只改变一个变量；页内同时记录输入事件、MapLibre 事件、以及 `easeTo` 是否落在 `[mousedown, 首次移动]` 窗口内）：

| 条件 | `dragstart` | 窗口内 `easeTo` | 失败次数（有/无 `easeTo`） |
| --- | --- | --- | --- |
| A 跟随运行 + 快速合成拖动（按下→移动约 8 ms） | 15/16 | 1/16 | 1 / 0 |
| B 相机静止 + 同一段输入 | 16/16 | 0/16 | — |
| C 跟随运行 + **真实人类节奏**（按下→移动约 60 ms） | **0/16** | 16/16 | 16 / 0 |
| F 与 C 同节奏，但手势期间不发 `easeTo` | **16/16** | 抑制 | 0 |

每一次失败都对应窗口内确实夹了一次 `easeTo`，无一次例外；F 与 C 只差「是否发动画」这一个变量，因此是因果而非相关。B 否证了「输入不足」假设，C 否证了「合成序列过快」假设——**把输入改得更真实反而使失败率升到 100%**，原用例之所以大多通过，恰恰是因为它的合成拖动只有 8 ms。真实用户按下后需 30–70 ms 才移动超过 3 px，因此真实拖动几乎必然被自己的跟随动画吞掉。

**修复（产品交互层，`app.js`，+83/−1）分两层，缺一不可：**

1. 指点按下期间不发起相机动画：`if (following)` → `if (following && !pointerDownOnMap)`。MapLibre 本就在 `mousedown` 时以 `_stop(true)` 取消进行中的缓动（该分支**不** reset handler），是我们随后发起的 `easeTo` 把它刚建立的手势状态抹掉。
2. 暂停判据取自**用户原始输入**（Pointer Events + 3 px 位移阈值），而不是可被自身动画抑制的库事件 `dragstart`；`dragstart` 监听保留作双重保险。阈值取 MapLibre 默认 `clickTolerance`，使产品对「拖动」的定义与库的定义不会分叉。`pointerdown` 挂在画布容器，`pointermove`/`pointerup`/`pointercancel` 挂在 window（拖动过程中指针会离开画布），另有 `blur` 复位与「鼠标移动但按键已抬起」的防御性复位。

语义边界刻意保持：普通点击（无位移）**不**暂停跟随——地图上没有点击交互，跟随不该因一次误触中断。恢复路径不变（◎ 按钮 + 既有的 8 s/速度自动恢复）。

**回归用例**（`09-follow.spec.mjs`，+117）：E2E-09d 用真实时间尺度（按住 60 ms 再移动）复现该窗口，断言四件事——跟随确实暂停、MapLibre 确实发出了 `dragstart`（只断言标志位会在「跟随暂停了但地图仍拖不动」时误判通过）、相机确实停止缓动、◎ 能重新启用；E2E-09e 锁定「普通点击不暂停」这一语义边界并证明跟随循环仍在驱动相机。60 ms 是**输入波形整形**（复现被测条件所必需），不是同步等待；其余等待全部是 `expect.poll` 对真实条件的轮询。无 retries、无 skip、未放宽断言。

**变异核验**：M-A 把 `pauseFollow` 改为空操作 → 4 项失败（`Expected: false / Received: true`），exit 1；M-B 只移除 `!pointerDownOnMap` 这一半 → E2E-09d 以「MapLibre 未识别出这次拖动（手势被跟随动画丢弃）Expected: >=1 Received: 0」失败，而 `following` 确实已变 false——证明两半都承重，且断言 (2) 能识破「只有标志位变化」的假通过。恢复后 `app.js` 哈希与恢复前一致。

案例 4 与 5 在修复前均为 exit 4，暴露了两个 harness 自身缺陷：

- **新鲜度比较根过粗**：编辑 `nav-core-cli/src/main.rs` 后，`od-corpus.exe` 被判「陈旧」（它并不依赖 `nav-core-cli`）。修复为依赖闭包（§9）。
- **`$old = if (...) { @(...) } else { @() }` 的数组展开**：语句作为表达式赋值时 PowerShell 会把单元素数组展开为标量，随后 `$old.Count` 在 `StrictMode 2.0` 下抛 `PropertyNotFoundException`，使基准维护模式的差异摘要判定失败。修复为显式先赋 `@()` 再在 `if` 内赋值。

随后又暴露第三个缺陷（案例 9）：`Get-CSharpSourceRoots` 用 `$x.Project.ItemGroup` / `$ig.ProjectReference` 访问 XML 属性，在 `StrictMode 2.0` 下遇到「该项目只有 `PropertyGroup`」或「该 `ItemGroup` 没有 `ProjectReference`」时抛异常（实测 `ScsHashFs.csproj`、`ScsSii.csproj` 与 `MapInspector.csproj` 的若干 ItemGroup 均如此）。修复为 `ChildNodes` + `LocalName` + `GetAttribute`，同时获得命名空间无关性。

这三个缺陷都由本批次自己的验证案例捕获，未进入最终结果。

### 17.6 clean-clone 过程

克隆保留在 `C:\Temp\ETS2Nav Clean Clone 7610f9\`（754 MB）供复核；`-RemoveClone` 可自动清理。

**§17「不得读取原工作区产物」的机器保证**：harness 的 `Assert-ExecutableAllowed` 拒绝执行任何既不在**当前 harness 所在仓库根**之下、也不是 PATH 上标准工具（`dotnet`/`cargo`/`python`/`cmd`/`powershell`）的文件。因此在克隆中运行时，任何对原工作区二进制的回退都会立即成为 HARNESS FAILURE 而不是悄悄通过；每条步骤日志也记录了实际执行路径与工作目录，可事后复核。C# 侧的测试输入路径由 `map-compiler/tests/SharedTestPaths/TestPaths.cs` 从**测试程序集位置**向上定位仓库根，因此克隆中的测试读的是克隆内的 `vendor/extracted`（或显式传入的 `ETS2NAV_EXTRACTED`），不会读到 `E:\Projects\Pi\ETS2Nav\vendor\extracted`。

## 18. 新发现问题

**本轮修复**（除 §2.3 的九处路径与 §2.2 的四类判定缺陷外）：

- `nav-core-cli speed` 与 `signal` 在「无路线」时打印到 stderr 后正常返回，进程退出码仍为 0：业务失败与成功在机器语义上不可区分。已改为 `exit(1)`。
- `nav-core-cli bench` 的 trace 由硬编码本机路径改为显式输入（`--trace` / `ETS2NAV_TRACE`），缺失时打印明确的跳过行。
- `CameraProbe`、`map-inspector`、`ferry-diag`、`speed-validator` 的缺省路径改为「显式参数 > 环境变量 > 仓库根相对路径 > 报错退出」，不再猜测用户磁盘位置。
- `mutation-validate.ps1` 的 `$web` 改为从 `$PSScriptRoot` 推导。
- `map-compiler` 的四个测试文件改用共享的 `TestPaths`（`map-compiler/tests/SharedTestPaths/TestPaths.cs`，三处 csproj 以 `Compile Include` 链接同一份实现）。
- `run-p1..p5-tests.bat` 重写为薄包装；README 的回归示例命令更新为不依赖本机路径的写法。

**登记未修**（附判断依据）：

1. **`nav-core-cli route` 的每-profile「无路线」分支仍以 exit 0 返回**（`main.rs` 的 `None => println!("[{}] 无路线", ...)`）。它不在 §9 的清单内、也不被任何回归步骤使用，故本轮只登记不改：修复方式与 `speed`/`signal` 相同（一行），但会改变一个已闭环命令的退出码语义，应由授权决定。同类的还有 `regression` 命令的 `不一致 N` 不参与其自身判定（本轮改为在 harness 层断言 `不一致 0`，产品判定未动）。
2. **`vendor/` 整个被 `.gitignore` 忽略**，因此干净检出没有 `vendor/extracted`、也没有 `tools/ets2nav-web/vendor/maplibre-gl.js` 与字体。影响面：P1–P5 可通过显式外部路径满足（本轮已证明）；但**前端套件无法在干净检出中构建**（`build.mjs` 需要 `vendor/maplibre-gl.js`），`npm run test:e2e` 只能在持有该 vendor 目录的工作副本中运行。§16 只要求 clone 内跑 P1–P5，故不阻塞本轮 Gate；但这是 Batch 5（CI）必须解决的问题——CI 需要在流水线里提供该 vendor 目录或改为把前端依赖纳入版本控制。
3. **被跟踪的构建产物**：`telemetry-plugin/scs-nav-bridge/out/*.obj|*.exp`、`telemetry-plugin/semaphore-bridge/out/*.obj|*.exp` 嵌有构建机绝对路径。应当从版本控制移除并改为构建生成（`out/` 未在 `.gitignore` 中）。
4. **五个集成测试在外部输入缺失时静默通过**（§17.3）。建议引入 `Xunit.SkippableFact` 把「未验证」与「通过」分开。
5. **`data/` 整个被忽略**，数据集只能外置传入。这本身合理（体量大、经 Release 分发），但 README 未说明 P2/P5 在干净检出上必须显式提供数据集；本轮已在 harness 的 preflight 报错信息中给出可操作指引。
6. **`nav-core-cli syntrace` 与 `dataset-reader-smoke` 没有业务判定**（前者只报告 `SYNTRACE OK` 与帧数，后者仅 exit 0）。它们的作用是「产物可被读取」，harness 以 exit 0 判定，并另有 trace 新鲜度与产物新鲜度断言。未改产品行为。
7. **P1 的 `python` 依赖已移除**：原来两处 `python -c`（哈希比对、`diagnostics.json` 解析）改为 PowerShell 实现。P1 的前置条件因此只剩 dotnet + 游戏数据 + 解包根——依赖面收窄，且不再是「未声明的外部依赖」。

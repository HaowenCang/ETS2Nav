## §5 Job Object fail closed（§4）

### §5.1 修改前的问题

原实现中作业对象失败只打印 WARN 然后继续运行。此时产品已经失去
「Desktop 被强杀 → sidecar 必定被回收」这一**发布性质**，而界面看不出任何异常。
更隐蔽的是第三个分支：作业对象建立成功但 `OpenProcess` 打不开进程句柄时，旧代码既没有
告警也没有判据（它落在 `else if job.is_none()` 之外），是一条完全静默的降级路径。

### §5.2 修改后的契约

```text
缺省：要求作业对象
  create 失败            → 启动失败，退出码 24，step=create，尚未派生任何子进程
  assign 失败            → 启动失败，退出码 24，step=assign，立即回收已派生的 sidecar
  进程句柄打不开         → 同上，step=open-process
  fail closed 一律不建窗口（返回发生在 tauri::Builder 构造之前）
显式降级：--allow-no-job-object
  → 允许继续，但必须留下 WARN，且状态可观测为 state=create-failed required=false
```

新增退出码 **24**（`kind=sidecar-job-required`），与既有 `0/2/20/21/22/23` 不冲突。
22 与 24 分开是刻意的：22 表示 sidecar 起不来，24 表示 sidecar 起来了但**发布性质的清理
保证**没有建立；把两者合并会让「作业对象没生效」在发布检查里不可观测。

### §5.3 注入方式

注入经 cargo feature `fault-inject`（**默认关闭**），而不是 `debug_assertions`。理由是
本轮要证明的性质是「**release 构建**在作业对象不可用时 fail closed」；若以
`debug_assertions` 为门，注入代码只存在于 debug，release 侧的判据就只能靠阅读代码推断，
而「编译通过不等于行为成立」正是本批次要消除的推理方式。因此：

```text
cargo build --release                        → 无注入代码（发布产物）
cargo build --release --features fault-inject → 有注入代码，且完整走 release 判据路径
```

两种构建使用**独立 target-dir**：cargo 对同一 package 的不同 feature 集合输出到同一个
`target/release` 路径，共用会让先构建的发布产物被注入构建覆盖，「随包二进制不含注入面」
这条性质会静默失效。

发布产物不含注入面由 `assemble-bundle.ps1` 强制：以 Latin-1 逐字节读取，断言
`ETS2NAV_JOB_FAULT`（Desktop）与 `ETS2NAV_FAULT_INJECT` / `ETS2NAV_FAULT_HOLD_MS`（sidecar）
均不存在，任一出现即 PRECONDITION FAILURE。

### §5.4 判定结果

`desktop/tests/job-object-gate.mjs`，实跑 **30 项断言全部 PASS**：

| 用例 | 内容 | 实测 |
| --- | --- | --- |
| J-01 | 正常 release 产物 | exit 0；`sidecar-job state=assigned required=true`；`job_required=true` |
| J-02 | 发布产物不含 `ETS2NAV_JOB_FAULT` | present=false |
| J-03 | 注入构建**含**该字面量（J-02 的正对照） | present=true |
| J-04 | create 注入 | exit 24；`step=create`；**未建窗口**；未派生 sidecar |
| J-05 | assign 注入 | exit 24；`step=assign`；`AssignProcessToJobObject win32_error=5`；未建窗口；**无残留 nav-core-cli 进程** |
| J-06 | 显式降级（release 与 debug 两种 profile 各一遍） | exit 0；`WARN kind=job-create-failed`；`state=create-failed required=false`；sidecar 仍被正常回收 |

J-05 的 `step=assign` 本身是「确实派生过子进程」的证明——该分支只有在 spawn 成功之后才可能
被记录。没有这条，J-05 的回收断言会退化成「本来就没起过任何东西」。

J-04/J-05 **刻意不传 `--no-window`**：在 `--no-window` 下窗口本来就不会被创建，
「不开窗口」的断言会退化成恒真。因此这两个用例跑在会开窗口的配置下，并带超时保护。

### §5.5 一处自救：判定脚本自身的空洞通过

该脚本首版因笔误没有把解析结果写进 `fields` 字段，于是 J-04/J-05 的
「未出现 window」「未出现 sidecar-started」这类**否定式**断言在空输出上恒真，全绿。
发现后除修正解析外，另加了一条前置断言：每次运行先断言 stdout 中确实出现
`[desktop] start`（证明通道被捕获），否则该运行的否定式结论无效。实测该前置在
六次运行中均给出 `stdout_bytes=880…1281`，确认捕获真实存在。

### §5.6 变异验证 M-JOB

将 `sidecar.rs` 中三处 `if spec.job_required {` 改为 `if false {`（即移除 fail-closed 判据），
重建注入构建后重跑判定脚本。**失败发生在预期断言上**，且失败形态就是该性质要防止的危害：

```
[FAIL] J-04 退出码为 24（sidecar-job-required） - exit=TIMEOUT
[FAIL] J-04 未创建窗口（fail closed 必须在建窗之前返回） - window={}      ← 窗口被创建
[FAIL] J-04 未派生 sidecar（create 发生在 spawn 之前） - sidecar-started={"pid":"38284",…}
[FAIL] J-05 已派生的 sidecar 被立即回收（无新增残留进程） - 泄漏 pid=[22548]  ← 真实孤儿
JOB OBJECT GATE: FAIL (11)
```

两个残留进程（pid 38284、22548，各占约 765 MB）在恢复后被显式清理。恢复源码后重跑
**30/30 PASS**，退出码 0。

这不是「只看 exit 非零」：变异体的失败恰好落在 `step`、退出码、窗口创建与进程残留这四条
预期断言上。

## §6 bundle manifest 隐私修复（§5）

### §6.1 缺陷

`assemble-bundle.ps1` 原先把 `basemap.source = $MapPmtiles` 与 `fonts.source = $FontsDir`
写进清单。传入 `E:\Projects\...` 或 `C:\Users\...` 时，**调用机器的绝对路径会进入公开
产物的 bundle-manifest.json**。

### §6.2 修复

清单升到 **schema 2**，`*.source` 被结构化 `provenance` 取代；同时新增
`profile`（按资源实际存在性测量的 CORE/FULL）与 `fonts.tree_sha256`。
schema 号递增使「旧 Desktop 读到新清单」与「新 Desktop 读到旧清单」都成为显式失败，
而不是静默忽略字段后给出看似正常的结论。`desktop/src/bundle.rs` 同步强制 schema 2。

provenance 的必需键：basemap 为 `kind/dataset/source_commit/game_version`；
fonts 为 `font/version/upstream/license_spdx/source_sha256/generator/generator_version/
generation_command/ranges`（`source_sha256` 另校验 64 位十六进制）。任一键的取值若匹配
「单字母 + 冒号 + 分隔符」的绝对路径模式即拒绝。该正则带前置字符类，
使 `https://` 不匹配（`https://` 中 `s` 之前的字符是 `p`，落在排他类内）。

提供了 `-MapPmtiles` 或 `-FontsDir` 却没有对应 `-Provenance` 时直接 PRECONDITION FAILURE：
发布资源必须有可核查来源，不得只记录本机路径。

### §6.3 修复过程中发现的真实缺陷：PowerShell 变量名大小写不敏感

修完上述内容后，用合成字体树驱动该路径时组装**失败**，报
`Cannot bind argument to parameter 'Path' because it is an empty string`。
逐层定位（脚本级打印证明 `-FontsProvenance` 已被正确绑定；函数级打印证明函数体从未执行；
隔离复现证明函数本身正确）后确认根因：

```powershell
$fontsProvenance = $null      # 清单累加器
…
$prov = Read-Provenance -Path $FontsProvenance   # 同名参数，已被上面覆盖为空
```

PowerShell 的变量名**大小写不敏感**，因此 `$fontsProvenance` 与 `-FontsProvenance` 是同一个
变量。初始化累加器为 `$null` 的那一行，把调用方传入的 provenance 路径抹掉了。
后果不是「报错」而是**静默**：更早的守卫（`-FontsDir` 与 `-FontsProvenance` 必须同时提供）
在覆盖发生之前已经通过，于是校验通过、组装成功、清单里的 provenance 为 null。
`$basemapProvenance` 与 `-BasemapProvenance` 存在同一冲突。

若本轮不实现 §7 的字体资源路径，这个缺陷不会暴露——它只影响 FULL profile，正是
「资源齐备的正式产物」那条路径。修复为把两个累加器改名为 `$fontsProvRecord` /
`$basemapProvRecord`。

### §6.4 ranges 与磁盘分片必须互相覆盖（§7）

原实现对 `ranges` 只要求「非空字符串」，从不与 `vendor/fonts/` 的实际内容交叉核对。
因此**声明 `ranges:"0-255"` 而实际放入任意同名文件即可通过全部检查**——这正是
「以存在性代替覆盖」在打包层的形态。现在双向核对：

```text
正向：provenance 声明的每个 range 都必须存在 <font>/<range>.pbf
反向：磁盘上每个 .pbf 都必须被声明覆盖，且其所在目录名必须等于声明的字体
```

`verify-bundle.ps1` 独立复核同一判据（含 `fonts.tree_sha256`），使「换掉内容、保持文件数」
不再能通过。

### §6.5 合成样本验证（真实字形资源不可得）

`assemble-bundle.ps1` 的字体路径在本环境无法用真实资源驱动，因此用合成树与合成数据集
建立独立验证：**14 项断言全部 PASS**。

| 用例 | 期望 | 实测 |
| --- | --- | --- |
| G-01a…g | 声明与磁盘一致 → 成功，且 profile=CORE（无底图不得冒称 FULL） | exit 0 |
| G-01d | **provenance 真的进入清单**（`fonts.provenance.font` 可读） | 可读 |
| G-01f | 隐私扫描器在含 provenance 的 bundle 上零 FAIL | exit 0 |

```text
Archive reproducibility = NOT CLOSED  （见下）
```

`-SourceDateEpoch` 在两次打包中取同一值，因此 `generated_at` 与所有文件 mtime 归一化到同一
瞬时，清单本身也逐字节一致。ZIP 由 `System.IO.Compression.ZipArchive` 直接构造（不用
`Compress-Archive`，后者不提供条目顺序与时间戳控制）：条目按 ordinal 排序加入、每个条目的
`LastWriteTime` 设为固定瞬时、压缩级别固定。

| 项 | A | B |
| --- | --- | --- |
| `source.commit` | `a6e570db2c503ec2367d71b42ee73ac1ab58f80f`（**historical superseded**） | 同 |
| ZIP 文件名 | `ETS2Nav-0.7.0-rc.1-windows-x64-core.zip` | 同 |
| ZIP 字节数 | 178091246 | 178091246 |

`Input freeze = STABLE`（打包前后两次输入快照完全一致，A/B 判定有效）。

**两次运行的独立性是可核查的**：B 的 `assemble-bundle` 做了一次**完整重编译**
（`Compiling ets2nav-desktop … Finished`），仍产出与 A 相同的
`0b354c7b…`（desktop）与 `90332b56…`（sidecar）。这既确认了 §17.1 的 `/Brepro` 修复，
也说明 `Archive reproducibility = PASS` 不是「因为第二次没重新链接」的假象。

**Archive reproducibility 由 NOT CLOSED 改判为 PASS 的依据**：`-SourceDateEpoch` 使
`generated_at` 与全部文件 mtime 归一化，ZIP 由 `ZipArchive` 以固定条目顺序与固定时间戳构造，
两次独立打包的 ZIP **逐字节相同**。

**其边界仍然成立**：本轮验证的是**同一环境、同一 .NET 压缩实现、同一时区**下的字节相等；
跨时区或跨运行时的字节相等**未验证**，因此不写「跨环境 byte reproducible」。

`nav-core-cli/src`、前端 dist 与数据集的树摘要），并打印
`Input freeze = STABLE | DRIFT DETECTED`；检测到漂移时**显式宣告 A/B 判定无效**。

### §17.1 二进制本身的可复现性（本轮新发现的缺陷）

在为一轮被判定无效的 A/B（见上）做根因分析时，顺带发现**两个 Rust 二进制本身不可逐字节
复现**：`ets2nav-desktop.exe` 从两个不同的 target 目录各构建一次，产物相差 **20 字节**。

差异经逐字节比对完全定位：

| 偏移 | 内容 |
| --- | --- |
| `0x100` | PE 的 COFF `TimeDateStamp`（链接时刻） |
| `0x3C6884` / `0x3C68A0` / `0x3C68BC` | 三个调试目录条目的时间戳（间隔 0x1C，即 28 字节的条目长度） |
| `0x3C6C48`…`0x3C6C57` | 一个 16 字节 GUID |

镜像内检索目标目录名得到 **0 命中**，因此差异不是路径泄漏，就是链接时刻。
`nav-core-cli.exe` 属同一机制。

**这是 Batch 6A 已经修过的同一类缺陷，但在 Rust 侧被漏掉了。** 6A 为 telemetry plugin 的
DLL 加了 `/Brepro`（`build.bat` 中同时作用于 `cl` 与 `link`），并把「三条不同绝对路径的
clean build 逐字节一致」写进了插件产物契约；但两个 Rust 二进制没有做同等处理。
后果直接落在本轮的判定上：sidecar 的字节身份被写进 `bundle-manifest.json` 并由 Desktop
每次启动校验，因此只要两次打包之间发生**重新链接**，`desktop_exe.sha256`、`sidecar.sha256`、
清单本身以及整棵 bundle 树的摘要都会变——§17 的 payload 可复现性与候选二进制冻结都不再稳定。

修复：`desktop/build.rs` 与 `nav-core/tools/nav-core-cli/build.rs` 在 MSVC 目标下发
`cargo:rustc-link-arg=/Brepro`（非 MSVC 平台不受影响）。

**验证（真实构建，非推断）**

| 对象 | 修复前 | 修复后 |
| --- | --- | --- |
| `ets2nav-desktop.exe` | 两个独立 target 目录相差 20 字节 | 两个独立 target 目录 sha256 **均为** `0b354c7b8ad45d659b95dee95f93f6ec1c2c1423d2b5f1717e74083f667773da`（4072960 B） |
| `nav-core-cli.exe` | 同机制 | 两个独立 target 目录 sha256 **均为** `90332b5618fd2f59fcd47d3ebb3d3b37df7ffb56e20a8dee76b2fe7de66b42b7`（2648576 B） |

由于二进制字节改变，所有以二进制身份或行为为判据的门都重跑了一遍（`Portable`、`CLI`、
`FaultContainment`、`Desktop`、`JobObject`、`--windowed` 窗口形态），结果见 §31.1。
前端、dataset、插件 DLL 与许可清单未改动，故未重跑对应门。

**边界**：`/Brepro` 消除的是链接器时间戳。它不承诺跨 MSVC 工具链版本、跨 Rust 版本或跨
机器配置的字节相等——本轮验证的是**同一工具链下重复构建**的确定性。
**Archive reproducibility 为何是 NOT CLOSED**：即使 payload 逐字节一致，ZIP 自身的字节
还取决于条目时间戳的时区表示与 .NET 压缩实现的版本。本轮只验证了**同一环境下重复运行**
的字节一致性；跨时区 / 跨 .NET 运行时的字节相等**未验证**，因此不写 byte reproducible。

## §20 RC tag / GitHub Release 状态

**本轮不创建 tag、不创建 GitHub Release。** 采用轮次指令允许的方案 A：最终 ZIP 保存在
本地 staging 并输出其 SHA-256 与 256 位校验和。

理由有三条，按权重排列：

1. 产品 RC 必须能与 dataset Release 区分（§21），而一旦创建 release 就需要同时维护
   asset 与 note 的准确性；
2. 该 release 的资产包含约 373 MB **ETS2 派生数据**，而 §30 明确要求不对派生数据的公开
   再分发许可给出新的法律保证——发布是不可轻易撤回的动作，属于用户决策而非工程默认；
3. 在 B1–B6 之前发布任何可下载产物，即使标注 prerelease，也会把「候选」变成事实上的
   分发渠道，而候选二进制尚未经实机验证。

**产物与校验和已产出且可核验**，下游只要一条 `gh release create --prerelease` 即可发布；
是否发布留给用户。若发布，release note 必须含
`REAL-GAME B1–B6 NOT YET VERIFIED`，且**不得**出现 `latest` / `stable` / `production` 字样
（现有 release note 模板已据此约束）。

未覆盖、未重写、未复用 `dataset-europe-v5` release。

## §22 Tauri localhost 信任面

**审计结论：删除。**

`security::CORS_ALLOWED_ORIGINS` 曾为 `["http://tauri.localhost"]`，其来源是 Batch 3 对旧
桌面壳（Tauri 2.11.5、`frontendDist` 指向静态前端）WebView2 握手的**实测**结果。
Batch 6A 改变了产品架构：窗口改为加载 sidecar 自己在回环端口上提供的页面，页面与 API
**同源**，浏览器不再发起跨源请求，于是该条目没有任何生产消费者。

按 §22「不得因为旧测试存在就保留已无产品消费者的信任例外」，本轮删除该条目：

```text
删除前：browser_origin_accepted = 自身同源 ∨ 白名单{tauri.localhost}
删除后：browser_origin_accepted = 自身同源
```

**机制保留、策略为空**：白名单判定与响应头生成改为按表参数化
（`cors_allowed_origin_in` / `cors_headers_in` / `preflight_headers_in`），
并以合成白名单单测 `cors_mechanism_works_for_a_non_empty_list` 证明其在非空时按契约工作
（精确相等匹配、预检逐项列举、无通配符）。这样「策略为空」与「机制被写坏」保持可区分，
且将来若真需要第二个受信来源，存在一个经过测试的登记点而不会退化成通配符。

**受影响断言的改判**（三处，全部是收紧而非放宽）：

| 位置 | 原判据 | 新判据 |
| --- | --- | --- |
| `security.rs` 单测 | `browser_origin_accepted(…, "http://tauri.localhost")` 必须为真 | 必须为假 |
| `server.rs` 单测 | 该 origin 必须获得精确 ACAO 与 `Vary` | 白名单为空时任何 origin 都不得获得 |

## §23 CSP 处置

**加入并验证通过。** 审计发现策略可以收紧到不含 `unsafe-inline` script：

```
default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline';
img-src 'self' data:; font-src 'self' data:; connect-src 'self';
worker-src 'self' blob:; child-src 'self' blob:; object-src 'none';
base-uri 'none'; form-action 'none'; frame-ancestors 'none'
```

依据是逐项核对过前端实际需求：`index.html` **没有**任何内联 `<script>`、内联 `<style>`
或内联事件属性，三个 vendor 包与 `app.js` 都是同源外部文件，地图 worker 是同源 `.js`
（`app.js` 用 `setWorkerUrl` 显式指向），字形 PBF、PMTiles、bootstrap 与 `/api/*` 全部同源。
`style-src` 保留 `'unsafe-inline'` 是刻意的：MapLibre 通过 HTML 字符串写入带 `style` 属性的
元素，去掉它会产出控制台报错而换不到实质防护（页面不渲染任何用户可控 HTML）。

CSP 加在 `security::HARDENING_HEADERS`（所有响应都带），因此不存在「某条响应路径漏加」的
可能。**未使用 `ws:` 通配**：`connect-src` 只允许 `'self'`。这一选择同时解决了一个副作用——
初版曾写 `ws://127.0.0.1:*`，其中端口通配的 `*` 触发了四条既有 CORS 断言
（它们的判据是「响应中不得出现星号」，作为「不得回通配符」的代理）。与其放宽那四条与
CORS 通配相关的检查，不如把策略收窄到不需要星号。

**验证**（真实浏览器，不是推断）：

| 验证 | 结果 |
| --- | --- |
| 真实 Chromium E2E | `46 passed` |
| browser-loopback | `8 passed` |
| LAN 矩阵 S1–S11 | `FAIL=0 NOT_VERIFIED=0 SKIP=0`（S8 输出中可见 CSP 头） |
| 真实 WebView2（`--windowed`） | `page_load=Finished`，`url=http://127.0.0.1:2794/`，`ws_clients=1` |

**边界**：局域网来源（`http://192.168.x.x:<port>`）的**浏览器行为**未被本轮独立验证；
其依据是同一条 CSP3 `'self'` 规则（`ws:` 与 `http:` 同主机同端口视为同源）。这一点如实
标注，不冒充已覆盖。

`CSP hardening = IMPLEMENTED AND BROWSER-VERIFIED (loopback origin)`。

## §24 worker hang / watchdog 处置

```text
Worker hang detection = DEFERRED
```

Batch 6A 解决的是 **worker 终止**（panic 或意外返回），本轮**未**解决 worker
**死锁/活锁**。做了设计审计，结论是低风险实现不可得，理由如下。

数据源线程有两条循环（`server_cli.rs`）：回放分支按帧节流推进；实时分支为
`loop { consume_dest(); match src.poll() { Fresh => …, Stale => sleep(50ms),
Disconnected => sleep(200ms) } }`。**有效的 heartbeat 应当表示「循环本身在推进」**，
在该实时循环里就是每次迭代递增的计数器——Fresh/Stale/Disconnected 三种状态都算推进。

不能使用的 heartbeat：**新鲜遥测帧**。游戏断开、暂停、`TelemetryState::Stale` 都是合法状态，
以帧为心跳会把合法状态误判为挂死。这一条是本轮明确写下的约束。

未实现的原因不是实现困难，而是**阈值无法标定**：判定挂死需要「最长合法迭代间隔」的上界，
它取决于 `TelemetrySource::poll()` 在真实游戏内存读取下的最坏耗时与 `on_frame` 的最坏耗时。
这两项都需要实机测量（B1–B6），本环境不具备。阈值取小会误杀一个正在正常工作的产品，
取大则退化为「事后才发现」，两者都比缺陷本身更糟。因此不实现、不猜阈值，登记为
DEFERRED，并把所需的标定测量写进 B1–B6 的前置清单。

**明确不延伸**：`FaultContainment = PASS` 只覆盖「worker 终止」这一失效模式，
**不代表所有 worker 失效模式都已覆盖**。

## §29 Release artifact 安全扫描

对**解压后的最终 artifact 树**执行 `scan-release-privacy.ps1`，输出每条命中的
文件、行号与上下文，并分类为 `FAIL` / `benign`（附理由）/ `REVIEW`（需人工判断）。

但不得被其它类误判。

**人工分类是强制的**：扫描器必须输出 FAIL / benign / REVIEW 三类计数，
「grep 零命中」不作为唯一逻辑。自检保证正样本能被抓到、负样本不被误伤。

## §35 附：本轮的自我否证记录

本轮有三处「先做错、后由证据推翻」的过程，按其对结论的实际影响记录，避免读者把报告中的
确定语气误读为过程顺利：

1. **A/B 的首次运行因并发写入而无效**（§17）。后果是证据不成立，与产品缺陷同等严重。
   本次的并发写入者包括本报告的维护者本人，因此这不是「环境问题」而是方法失败。
   加固措施（输入指纹 + 漂移即宣告无效）已落进流水线。
2. **字体 provenance 的静默丢失**（§6.3）。它是 PowerShell 的大小写不敏感语义造成的，
   只在 FULL profile 路径上出现，而该路径在本环境无法用真实资源驱动——若不用合成样本
   主动驱动它，这个缺陷会原样进入正式产物。
3. **两处「测试自己写错」**：判定脚本的否定式断言曾在空输出上空洞通过（§5.5）；
   字体用例曾把 `profile` 期望写成 FULL、并用朴素正则自检隐私（§6.5）。
   两处都不是产品缺陷，但都会产出**假绿**，因此同样按缺陷处理。

4. **报告初版的 §0 把 `Existing required CI` 与 `P4R Batch 6B gate` 直接写成 `PASS`，而写下时
   最终 head 的 required check 尚未被观察到，且其前一个 head 的 `Source Gates` 是失败的。**
   这是先于证据的声称，与本轮反复强调的纪律冲突。修订把它改为指向一次被实际观察到的运行编号；
   记在这里而不是悄悄改掉，是因为读者需要知道报告自身也曾犯过它要求别人不犯的错误。

5. **门控判据依赖了编码。** 我把 Source Gates 的隐私自检断言写成匹配扫描器输出的**中文**。
   子进程 stdout 经管道回到父 PowerShell 时按控制台代码页解码，runner 上中文变成 `?`，
   于是断言在本地通过而在 runner 上必然失败——判据依赖了与被判性质无关的东西。
   修复为纯 ASCII 汇总行；并在本机把 `[Console]::OutputEncoding` 设为 437 **复现**该损失，
   确认 ASCII 断言仍然匹配、而旧的纯中文断言在同一输出下确实匹配失败。
   边界值得记清：该风险只出现在「Windows PowerShell 子进程输出非 ASCII」这一组合；
   Rust 与 node 子进程输出 UTF-8 字节，编码不受影响——因此 `CLI` 套件中匹配中文的既有断言是安全的。

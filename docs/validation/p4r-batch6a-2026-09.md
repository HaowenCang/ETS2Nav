## 2. MapLibre critical advisory 的处置与兼容性验证（§2）

**结论：CLOSED。** `tools/ets2nav-web` 依赖树内不再存在受影响版本，且该判定不依赖 advisory 数据库。

advisory 经 GitHub advisory API 逐字核对（不是转述）：`GHSA-jrc7-96c5-q579` / `CVE-2026-85061`，severity `critical`，CVSS 3.1 = 10.0，`vulnerable_version_range: "<= 6.4.0"`，`first_patched_version: "6.4.1"`，缺陷性质是 `DOM.sanitize()` 在遍历活的 `NamedNodeMap` 时删除属性导致跳过相邻属性（attribution control 的零点击 XSS）。

处置：精确钉到 `6.4.1`（不用 `latest`，不用范围），三处一致——`package.json` 的 `dependencies["maplibre-gl"]` 字面量、`package-lock.json` 的 `packages["node_modules/maplibre-gl"].version` 与根依赖声明、实际安装树。四个受保护依赖的 `version` 与 `integrity` 逐字节未变（pmtiles 4.5.0 / qrcode 1.5.4 / esbuild 0.28.2 / @playwright/test 1.63.0）。

`npm audit --omit=dev`（在 `tools/ets2nav-web` 内执行；首次在仓库根执行得到的是**无效结论**，因为那里没有 `package.json`，已在报告外更正）：

```text
升级前：maplibre-gl <=6.4.0  Severity: critical  GHSA-jrc7-96c5-q579
        1 critical severity vulnerability                                   exit 1
升级后：found 0 vulnerabilities                                              exit 0
```

**升级暴露的三处真实 v6 破坏**（都不是"顺手改"，不修就无法构建或运行）：

1. **v6 只发布 ESM**：`dist/maplibre-gl.js` 不存在，`main`/`unpkg` 字段为 `undefined`。原 `build.mjs` 直接复制该 UMD 文件 ⇒ 构建失败。改为用 esbuild 把 `dist/maplibre-gl.mjs` 打成 IIFE 到 `dist/vendor/maplibre-gl.js`（全局 `maplibregl`），`index.html` 的经典 `<script>` 形式保持不变。
2. **打包后库无法自行定位 worker**：`import.meta` 被替换为空对象，`getWorkerUrl()` 返回空串，`new Worker("")` 必败 ⇒ 地图永不进入 `loaded`。改为 `app.js` 在构造 `Map` 之前显式 `maplibregl.setWorkerUrl(new URL("vendor/maplibre-gl-worker.js", document.baseURI).href)`，并在 `build.mjs` 中断言该接线。worker 必须是 `.js` 而非 `.mjs`：nav-server 只把 `.js` 映射为 `text/javascript`，`.mjs` 会落到 `application/octet-stream`，配合 `nosniff` 被浏览器以 MIME 严格校验拒绝。**`vendor/maplibre-gl-worker.js` 因此被加入 `$script:FrontendArtifacts`**（它缺失是功能性缺失，不是视觉降级）。
3. **`Map.isEasing()` 在 v6 被移除**（仅存在于未导出的 `Camera`）：E2E-09 与 E2E-09d 抛 `TypeError: map.isEasing is not a function`（探针运行 2 failed / 7 passed，exit 1）。改用语义重合的 `Map.isMoving()`（v6 在 `_prepareEase` 置 `_moving=true`、`_afterEase` 置 `false`，与 `_easeFrameId` 同一时机）。**断言数量、方向与超时均未改动。**

**Batch 4 修过的 drag + `easeTo` 交互按最严要求复验**：反汇编 6.4.1 产物确认 `easeTo` → `_stop(!1,easeId)` → `HandlerManager.stop()` → `DragMoveHandler.reset()`（`delete this._lastPoint`），且 `dragMove` 仍以 `if(!n)return` 提前返回——Batch 4 针对的致命窗口在 v6 中**结构完全相同**，`following && !pointerDownOnMap` 守卫仍然必要且充分，`app.js` 的拖拽逻辑无需改动。E2E-09/09b/09c/09d/09e 全部通过。

**新增版本门** `tools/ets2nav-web/scripts/verify-maplibre-version.mjs`：离线只读本地文件，断言（a）已安装版本是合法 semver 且 `>= 6.4.1`；（b）lockfile 与之相同；（c）`package.json` 是精确钉版且等于该版本；（d）lockfile 根依赖声明与之一致。advisory 下限写成脚本内常量 `ADVISORY_FLOOR = "6.4.1"` 并注明 GHSA/CVE，因此**同一 commit 的结论不随 advisory 数据库变化**——这也是不把 `npm audit` 做成永久 required check 的原因。

**明确的范围边界**：`tools/graph-debugger/index.html` 仍引用 `unpkg.com/maplibre-gl@4.7.1`，因此**仍在受影响范围内**。本轮刻意未改：v6 不发布 `dist/maplibre-gl.js`，单独改版本号只会得到一个必然 404 的 URL；且该工具当前根本无法运行（其内联脚本语法错误、并使用从未存在的 `type:'pmtiles'` source，见 §19）。因此本轮的声称是「`tools/ets2nav-web` 的依赖树内 advisory 关闭」，**不是**「仓库中不存在任何受影响引用」。

## 3. 数据源 worker 的故障遏制架构（§3）

**问题形态**：修改前数据源线程由 `std::thread::spawn` 建立且 `JoinHandle` 被丢弃，主线程阻塞在 `listener.incoming()`。线程 panic 只终止该线程——进程存活，HTTP listener 继续接受连接并返回 200，而 `latest_json` 永远停在同一帧。这与「网络卡了」「UI 没刷新」在观测上不可区分；Batch 5.5 定位到的 `session.rs:454` 越界索引正是这个形态。

**架构**（`nav-core/tools/nav-core-cli/src/fault.rs`）：

```text
source worker (nav-source，thread::Builder 命名)
  ↓ JoinHandle::join 返回（Ok(()) 或 Err(payload)）——阻塞等待，不是轮询
supervisor 线程 (nav-supervisor)
  ↓ 抹除令牌 → FatalBus::report（Mutex + Condvar，事件驱动）
主线程：FatalBus::wait 被唤醒 → 输出致命诊断 → 显式断开全部 WS 客户端 → process::exit(70)
```

三点设计取舍：

- **不采用 `catch_unwind`，而用 `JoinHandle` 监督**。`join()` 同时捕获 panic 与「意外正常返回」两种终止；且不需要论证 `AssertUnwindSafe` 的边界——unwind 后从不复用任何状态，因为进程随即退出。
- **主线程不再阻塞在 `listener.incoming()`**。accept 循环移入独立线程 `nav-http`，主线程阻塞在 Condvar 上，因此「worker 死亡」到「进程开始退出」之间**没有轮询周期**。accept 循环保持阻塞语义而不是改成 nonblocking + 有界轮询：阻塞式 accept 不为连接接入引入任何额外延迟，而「停止正常业务」由**每请求**的降级判定保证。
- **降级状态只有一个真值来源**。`ServerCtx.fatal`（`Arc<FatalBus>`）既驱动主线程退出，也被 `handle_conn` 在解析请求**之前**读取：一旦置位，所有请求一律 `503 {"error":"data source failed","retryable":false}`。刻意不另设布尔副本（两处状态必然漂移）。选择让 listener 继续 accept 而不是关闭它，理由是可判定性：关闭 listener 会让客户端只看到「连接被拒绝」（与「服务没起来」不可区分），且降级分支本身将无法被任何测试触达，等于发布一条未经验证的代码路径。

**停机顺序**：致命诊断（stderr）→ `close_all_clients`（先发 RFC6455 close 1001，再 `shutdown(Both)`，整体预算 1 s，单连接写超时 200 ms）→ `process::exit(70)`。因此已连接的客户端看到的是**明确的连接结束**而不是中止。

**退出码 70** 与既有码位分离：`1` 是启动/业务失败，`2` 是用法错误，`101` 是 panic 默认码。沿用 `1` 会让观测方无法区分「服务从未起来」与「服务起来后数据源死了」——处置完全不同。用法文本已同步写明（`main.rs` 的 `usage()`）。

**令牌不进入日志**：`redact_secret(text, secret)` 在输出路径上做无条件替换。原因是 panic payload 的内容在构造上不受本模块控制，与其论证「当前没有这样的调用点」，不如让「stderr 不含令牌」成为结构性性质。单元测试用「payload 里意外含令牌」这一最坏输入锁定它。

## 4. 故障遏制测试（§4）

**判据是主动制造故障**，不是等某个偶发 panic。测试专用注入钩子 `fault::inject` 由 `#[cfg(debug_assertions)]` 门控：

```text
ETS2NAV_FAULT_INJECT = source-panic | source-exit
ETS2NAV_FAULT_HOLD_MS = <毫秒>   （仅延长致命退出的**时机**，不改变任何判定顺序）
```

不做 `/api/panic`、`--panic-now` 之类的控制面：那会把「远程可触发进程自杀」变成产品面。环境变量只能由已经能启动该进程的本机调用方设置，不扩大任何攻击面。release 构建里 `inject` 模块整体不存在，连环境变量名字面量都不进入二进制。

**为什么需要 `HOLD`**：产品在降级窗口内只停留微秒级（唤醒是 Condvar、接线是 shutdown），因此「降级期间 listener 仍会按健康语义回答吗」在观测上不可判定。该旋钮把窗口拉长到可观测量级，使 FC-02 成为确定性断言而非竞态抽样。它只在 debug 存在，且**只延迟退出、不改变顺序**——降级置位与客户端断开仍先于延迟发生。生产窗口的上界由**不带延迟**的运行测得。

`tools/ets2nav-web/scripts/run-fault-containment.mjs`（`npm run test:fault-containment`）覆盖：

| 编号 | 判据 | 实测 |
| --- | --- | --- |
| FC-01 | worker 终止被 supervisor 观察 | stderr 出现注入点原文 + `[desktop]`… 实为 `[server] FATAL class=SOURCE_WORKER_PANIC`；`source-exit` 时 `class=SOURCE_WORKER_EXIT` |
| FC-02 | 服务端不保持假健康 | 降级窗口内 `/api/snapshot` 与 `/api/bootstrap` 均 503；**zombie 窗口（最后一帧 → 进程退出）min 28 / median 34 / p95 41 / max 41 ms（n=5）**，上界断言 3000 ms |
| FC-03 | 进程有界非零退出 | 恰为 70；并新增「在 8000 ms 内退出」这条独立判据（见下方修正） |
| FC-04 | stderr 有明确致命类别 | `FATAL class=…` 前缀由产品与测试共用同一常量 `FATAL_MARKER` |
| FC-05 | stderr 不含会话令牌 | 逐个场景对 64 位令牌做子串检查 |
| FC-06 | 已连接 WS 客户端失去连接 | 收到 close 1001（不是停在最后一帧），含降级窗口内已被断开 |

合计 **52 条断言、失败 0**，三个场景（panic / 意外正常返回 / 降级窗口，前者重复 5 次）。

**测试自身的一处修正（本轮自我否证）**：首版脚本对「进程退出」做无界等待。去掉致命上报的变异体因此让整个套件**挂住 22 分钟**——挂住不是失败，它既无诊断也无退出码。已改为有界等待（8 s，实测优秀实现约 30 ms），并在超时时**显式杀掉进程**避免留下仍在监听的孤儿；降级窗口场景中的三处等待也改为「不抛」版本，使产品失败记为判据失败（exit 1）而不是 HARNESS FAILURE（exit 4）。judge 契约里 1 与 4 含义不同，把产品失败报成 harness 失败会把观测方引向测试而不是产品。

**release 侧的纯性**由 `CLI` 套件以**字节扫描**断言：release 二进制不得含 `ETS2NAV_FAULT_INJECT` / `ETS2NAV_FAULT_HOLD_MS` 字面量。反向断言（debug 二进制**含**这两个字面量）在故障遏制脚本的前置检查里——两侧合起来才排除「字符串拼写漂移导致双方都通过」。

## 5. Desktop 架构决策（§5）

**选择方案 1：sidecar 自己提供页面，WebView 加载 `http://127.0.0.1:<运行时端口>/`。**

```text
ets2nav-desktop.exe
  └─ spawn <bundle>/nav-core-cli.exe server <dataset> --port=0 --web=<bundle>/web
       └─ 同时提供 UI 与 API/WS
  Tauri WebView ── 加载 http://127.0.0.1:<运行时端口>/
```

不选「`tauri.localhost` 静态前端 + 跨源访问回环 API」的理由，按权重排列：

1. **同源使安全模型完全复用**。页面与 API 同源，于是 bootstrap、WS、`/api/*` 与普通浏览器走同一条路径——而那正是被 E2E（46 例）与安全套件（BLS-01…09）反复覆盖的路径。跨源模型需要 CORS 许可，并把令牌跨源交给页面，是一条**只服务于桌面壳**的额外信任关系。
2. **前端零改动即可工作**，这一点是实测而非推断：`app.js` 的 `sameOriginWsUrl()` 对任何 http 页面按 `location.host` 推导同源 WS 地址（`DESKTOP_HOSTS` 只排除 `tauri.localhost`），`httpBase()` 同源时直接返回 `location.origin`，`isLoopbackHostname("127.0.0.1")` 为真因而会走 bootstrap。`index.html` 里的 `ws://127.0.0.1:8123/ws` 只是 `file://` / `tauri.localhost` 情形的回退默认值，本模式下不会被用到。
3. **端口在运行时协商**，不存在「8123 被占用就永远连不上」的固定端口假设（§7）。

`desktop/tauri.conf.json` 因此不再声明 `frontendDist` 与静态窗口：窗口在 `setup` 里以运行时 URL 建立。代价是 bundle 必须包含前端产物与 sidecar——这正是本轮要建立的发布边界。

**保留的 Batch 3.5 Tauri Origin 契约**：`security::CORS_ALLOWED_ORIGINS` 仍为 `["http://tauri.localhost"]`，未删除。理由与边界都写清：它是为**既有壳形态**保留的信任关系，当前产品**不再使用**它；新脚本 `verify-desktop-origin.mjs` 同时证明两件事——（a）新产品的页面确实由 sidecar 自己提供（同源，且 host 不是 `tauri.localhost`）；（b）该白名单仍然**按契约工作**（白名单 Origin 在 `/api/bootstrap` 上被接受并回带 `Access-Control-Allow-Origin`，非白名单被 403 且不回许可头，任何响应都不出现通配符）。若不说明（b），白名单会变成一条无人使用也无人验证的信任关系。**是否删除这条已不被产品使用的许可，登记为 Batch 6B 的决策项**（删除会触及 BLS-08 与 security 单测，属于安全面变更，不宜在一轮"必须收绿"的工程里顺带做）。

`BLS-07` 的判定方式随之重写（脚本由 `verify-tauri-origin.mjs` 更名为 `verify-desktop-origin.mjs`，npm 脚本为 `verify:desktop-origin`）。旧判据的前提——「应用页面在 `tauri.localhost`、API 在另一个端口，因此可经固定端口转发器观测 Origin」——在新架构下不再成立（Desktop 自己协商端口并直连它启动的进程）。保留一个永远失败的检查不是"保留契约"，而是把它变成噪声。

## 6. sidecar 的二进制身份（§6）

**bundle 布局**（`desktop/scripts/assemble-bundle.ps1` 产出）：

```text
<bundle>/
  ets2nav-desktop.exe          产品入口
  nav-core-cli.exe             sidecar（127.0.0.1:<运行时端口>）
  bundle-manifest.json         身份清单（schema=1）
  web/                         前端产物（由 sidecar 提供）
  data/europe-v5/              数据集
```

解析规则刻意严格、**无任何开发目录回退**：

```text
bundle root = 当前可执行文件所在目录
sidecar     = <root>/nav-core-cli.exe 或 <root>/nav-core-cli-<triple>.exe（清单声明名优先）
web root    = <root>/web
dataset     = <root>/data/europe-v5
manifest    = <root>/bundle-manifest.json
```

不提供「回退到 `nav-core/target/debug/nav-core-cli.exe`」这类便利路径，因为那会让「打包正确」与「开发机上恰好有编译产物」在观测上不可区分。

**启动时的身份校验**：读 `bundle-manifest.json`，比对自己（`desktop_exe`）与 sidecar 的 SHA-256 与字节数。

- 一致 ⇒ `identity=verified`（清单同时记录 `source.commit`，运行日志中一并打印）；
- 内容不符 ⇒ **exit 20**，不开窗口（身份不符是打包缺陷，继续启动等于启动一个身份未知的可执行文件）；
- 清单缺失 ⇒ release **exit 20**；debug 允许但显式打印 `identity=unverified-no-manifest`（开发回路需要，且如实标注）。

SHA-256 为自实现（`desktop/src/sha256.rs`，零新增依赖），正确性由 FIPS 180-4 向量锁定：空串、`abc`、448-bit 边界、以及 1,000,000 个 `a` 的长消息向量；另有「任意分块喂入得到同一摘要」的增量契约测试。

**实测记录**（debug bundle，运行日志逐字）：

```text
[desktop] sidecar path=C:\...\b6a-bundle-debug\nav-core-cli.exe
          sha256=9fc4ec3e782b9f2913b6c04647748eff7a8f078113d513369e6fdfdd7f015ca3
          bytes=3801088 source_commit=b4184f79662e88ba8585505e0812c8e50083018e identity=verified
```

**一处必须说明的语义**：身份校验比对的是**内容**而不是路径。因此把一个与随包 sidecar 字节相同的二进制放在 bundle 之外并指过去，校验会（正确地）通过；§20 的 M3 变异因此使用 workspace 的 **release** 二进制（它与随包 debug sidecar 内容不同）来表达「启动路径指向 bundle 之外的另一个二进制」。

## 7. 端口协商（§7）

sidecar 以 `--port=0` 启动，由内核分配端口；Desktop 从 sidecar 的 **stdout** 读取精确契约行：

```text
[server] port=<十进制>
```

三点理由：端口信息必须能传（否则「端口被占用」只能表现为「窗口打开了但永远连不上」）；stdout 是机器通道而 stderr 是诊断流（中文、人类可读、可能被日志系统改写或缓冲）；**令牌不经此通道**——它只经回环 `GET /api/bootstrap` 交付，与普通浏览器同一路径，因此「令牌经命令行/环境变量/URL query 泄漏」这条路径在设计上不存在。

两侧都拒绝宽松匹配：desktop 侧 `sidecar::parse_port_line` 只接受 `^\[server\] port=(\d+)$`，并有单测锁定 `listening on 127.0.0.1:8123`（含 `[server] port=` 之外的任何变体）、`port=`、`port=abc`、`port=70000`、`ports=80` 全部返回 `None`——宽松匹配会把某天多出来的一行日志误判成端口，从而连到错误端口上。

**就绪判据不是「端口已绑定」而是 `GET /api/bootstrap` 返回 200**：server 在 `bind` 之后仍要读取 `search.db`，因此「已绑定」不等于「已可服务」。实测 `ready_ms` 约 600–2300 ms（热缓存）。

`--lan` 默认关闭：桌面应用不得在用户未要求时扩大本机网络暴露面；需要手机作为第二屏时显式加。这是对既有行为的**收窄**（此前用户手工运行 server 时可自行决定），已在 README 写明。

`desktop/tests/desktop-lifecycle.mjs` 的实测结果（被测对象是 **bundle 内的 exe**，不是 `desktop/target` 下的开发产物）：

| 编号 | 判据 | release bundle | debug bundle |
| --- | --- | --- | --- |
| D-01 | 身份校验 → sidecar 启动 → 端口协商 → bootstrap 200 → WS 收到实时帧 → 路线请求触发 `map_state` → 正常停机并回收 | PASS | PASS |
| D-02 | 数据集缺失：exit 21、stderr 带 `kind=dataset-*`、**未启动 sidecar、未协商端口**（不存在「窗口开着但连不上」） | PASS | PASS |
| D-03 | sidecar 无法加载数据集：exit 22、stderr 带 `kind=sidecar-start` | PASS | PASS |
| D-04 | 正常退出后 sidecar 进程消失（按 pid 查 `tasklist`） | PASS | PASS |
| D-05 | **Desktop 被强杀**后 sidecar 仍被回收（并先证明强杀前确实在运行，避免空洞断言） | PASS | PASS |
| D-06 | sidecar 运行期被外部终止：Desktop 检测到并以 exit 23 结束、stderr 记录 `kind=sidecar-exited` | PASS | PASS |
| D-06p | sidecar panic（exit 70）同样被检测为 23 | NOT VERIFIED（release 无注入钩子，见下） | PASS |

| D-01w | 真实 WebView：窗口创建 → `page_load=Finished` → 服务端观测到 UI 自己的 WS 连接（`ws_clients>=1`） | 本机实测 PASS | 本机实测 PASS |

断言计数：release bundle 21 条全通过；debug bundle 23 条全通过；窗口形态另加 3 条（在 debug bundle 上实测 23 条含窗口项）。窗口形态用 `--windowed` 在本机（交互式桌面）执行，**不在云端 required 步骤内**——hosted runner 无交互式桌面，报告据此如实区分「在哪里被验证」。

**无孤儿的三重保障**（强度递减但互相独立）：

1. **作业对象** `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`（`desktop/src/winproc.rs`）：Desktop 自身被强杀时句柄关闭，内核终止作业成员。这不是「更好的清理代码」，而是把清理从用户态职责变成内核保证——弱形态（只在正常退出路径 kill）无法覆盖任务管理器结束进程这一情形，那会留下一个仍在监听端口的 nav-server，恰好是本轮要消除的 zombie 形态换了个位置。
2. 停机路径显式 `TerminateProcess`，并 `wait_exit` 回收。
3. `Drop` 守卫：未走停机流程就被丢弃时仍终止子进程。

作业对象创建/加入失败不致命，但会**显式打印** `kind=job-create-failed` / `kind=job-assign-failed win32_error=<n>`，因为此时只剩第 2、3 重保障，而「Desktop 被强杀也不留孤儿」这一条不再成立——静默降级会把一条保证变成假设。

**sidecar 意外退出时不做自动重启**，而是明确报错并以 23 退出。理由与「不给 Playwright 加 retry」同源：自动重启会把产品缺陷藏在一个重试后面，而且需要处理「旧 session token 失效 → bootstrap 刷新 / WS 重连」的一整套时序（§8 允许选择「明确报错并退出」）。当前行为是：Desktop 检出 → 关窗/停机 → exit 23，绝不静默停摆。

**一处产物缺口**：`--no-window` 模式不建立 Tauri 事件循环，因此 `on_unexpected_exit` 回调里没有 `AppHandle` 可用；该模式下由主线程的 `wait_exit` 负责检出（实测 D-06/D-07 均通过）。窗口形态下由 `AppHandle::exit(23)` 结束事件循环。

## 9. 数据集运行时契约（§9）

选择 **A：release bundle 内包含数据集**（`<bundle>/data/europe-v5`），理由是「portable/release bundle 可完全离线运行」；体积代价已实测：373,674,105 B / 7 个文件。

契约分两层，边界明确：

- **启动时（每次）**：校验目录存在、必需文件齐备（`manifest.json` / `routing.graph` / `junction.graph` / `search.db`）、文件数与总字节与清单一致。**不重算 373 MB 的树摘要**——启动延迟是用户直接感知的量，而完整摘要由打包校验承担。该取舍的后果写在明处：等大小等数量的内容篡改不会在启动时被发现，而是由打包校验发现。
- **启动时（`--verify-dataset-digest`，默认关闭）**：重算整棵数据集目录的规范化树摘要并与清单比对。本轮 M5 变异证明它确实拦得住（见 §20）。
- **打包校验（`verify-bundle.ps1`，无条件）**：重新从磁盘读取 desktop/sidecar 的 SHA-256 与字节数、`web/` 与 `data/europe-v5` 的文件数/总字节/树摘要、basemap 与 glyphs 的存在性标记是否与磁盘一致。它刻意不信任组装步骤的内存状态。

树摘要算法由 Rust（`desktop/src/bundle.rs::tree_digest_lines`）与 PowerShell（`desktop/scripts/BundleCommon.ps1::Get-TreeDigest`）**各实现一次**：按相对路径的 **ordinal** 序排序（PowerShell 的 `Sort-Object` 是文化敏感比较，必须显式用 `StringComparer::Ordinal`，否则某些输入下与 Rust 的字节序比较不一致），每行 `rel\0size\0sha256\n`（UTF-8），对整串再做 SHA-256。两个实现的一致性不是靠阅读保证的：`--verify-dataset-digest` 用 Rust 实现去核对 PowerShell 写出的摘要，实测一致（`3f30272dc992d08d6831374b513647a9970c4cc484525b65db706965f474d91b`）。

清单同时记录数据集**自身的** provenance（`dataset_version` / `game_version` / `content_fingerprint` / `generated_at`，逐字取自数据集内的 `manifest.json`），因此一个 bundle 可以追溯到确切的提取批次。

本轮**不发布新数据集**，沿用既有 Release 附件。

## 10. 正式地图资源与字体的发布契约（§10）

**Release basemap completeness = PARTIAL。Release city-label completeness = PARTIAL。**

现状审计：

- 底图由 `map-compiler/src/ScsVectorTiles`（`TileBuilder` + `PmtilesWriter`）生成，输入是 P1 编译链的地图模型与切片，**需要正版游戏资源**；因此它属于本地/发布完整门，hosted runner 无法生成。数据集 Release 附件不包含 `map.pmtiles`。
- 前端 style 的 `glyphs` 指向**同源**本地路径 `vendor/fonts/{fontstack}/{range}.pbf`（不指向任何运行时公共 CDN）；`app.js` 先探测 `vendor/fonts/<fontstack>/0-255.pbf`，缺失时**跳过 city 文字层**并输出 WARN，几何图层照常。`build.mjs` 把 `<web>/fonts` 复制到 `dist/vendor/fonts`，缺失时同样只告警（属「离线视觉完整性」而非构建门）。

本轮完成的**契约**（真上传留给 Batch 6B）：

- `assemble-bundle.ps1` 支持 `-MapPmtiles <归档>` 与 `-FontsDir <目录>`；未提供时在清单里**如实记为 absent**，不把「没有底图」的包写成完整离线产品。字体的目标路径按前端实际请求的路径写入 `web/vendor/fonts`（写错目录不会报错，只会让文字层静默消失，因此由 `verify-bundle.ps1` 用同一路径核对）。
- 使用这两个参数时若源路径不存在 ⇒ PRECONDITION FAILURE（exit 3），不静默降级。
- 清单记录 `basemap.present/sha256/bytes/source` 与 `fonts.present/files/bytes/source`；`verify-bundle.ps1` 校验存在性标记与磁盘一致，若存在则校验摘要/计数/字节，并要求 basemap 非平凡（>1024 B）。
- **明确不使用 `PmtilesFixture` 代替正式欧洲地图**：E2E 用它生成合法归档是为了测试地图渲染路径，它不是发布资源。

若 Batch 6B 要公开声称"完整离线导航 UI"，两者都必须解决到与该声明相符：底图需要真实 Europe `map.pmtiles` 并经过独立 PMTiles consumer + Chromium 渲染验证；字体需要记录来源、license、转换工具、glyph PBF 生成流程与 SHA-256，且不得在运行期从公共 CDN 读取。

## 11. SCS SDK 的来源与摘要（§11）

建立 `scripts/prepare-scs-sdk.ps1`：固定官方 URL 与文件名、固定预期 SHA-256、下载后计算摘要并在不符时**立即失败**、解压到 gitignored 位置、检查必需头（直接 include 与传递闭包共 15 个）、校验每个解压文件与其归档条目字节一致、打印 `HEADER_DIR` 供调用方使用。`-Offline` 禁止下载但**从不跳过校验**；缓存存在时每次仍重算摘要。

```text
url       https://download.eurotrucksimulator2.com/scs_sdk_1_14.zip
filename  scs_sdk_1_14.zip
sha256    c6c1f7376b7324994d9f9c567f3c4141fbbf305b6bf803bc4cfeef2437b2023a
```

## 13. 插件可复现构建与产物身份（§12/§13）

**可复现性实验（先测量，再改）**：同一 MSVC 工具集、同一 SDK 归档摘要、同一源码 commit、同一 flags，从**三个不同绝对路径**各做一次 clean build（每个构建根各持一份解压后的 SDK，因此 `/I` 路径也不同）。

- 修复前**不**逐字节一致：两个不同路径的构建恰好差 2 字节，都是 COFF `TimeDateStamp`——偏移 `0x100` 以及它在唯一的 `coffgrp` debug directory 条目中的副本（偏移 `0x1D2D4`），来源是 3 秒的时钟差。
- 排除项（逐项扫描，不是假定）：镜像内无绝对路径（`E:\`、`C:\Users\`、`C:\Program Files`、`Projects\`、构建根名、通用 `[A-Za-z]:\\` 全部 0 命中）、无 PDB/CodeView（`RSDS`/`NB10`/`.pdb` 全部 0 命中）、源码无 `__FILE__`/`__DATE__`/`__TIME__`（唯一 pragma 是 `pack`）、三次构建工具集相同。
- 修复：两条 `build.bat` 的 `cl` 与 `/link` 行都加 `/Brepro`，并**验证其生效**（时间戳变为内容派生值、出现新的 `IMAGE_DEBUG_TYPE_REPRO` 条目、改源码会改变摘要与时间戳、不改源码重建不变）。
- 结果（三条路径 + 仓库内就地重建全部一致）：


## 20. 变异验证（§13/§20）

每个变异：施加一处**锚点唯一**的编辑 → 运行**本该抓住它**的那个门 → 断言门失败**且失败落在预期断言上** → 还原（并强制刷新 mtime，见下）→ 再跑一次门并断言恢复为通过。

| --- | --- | --- | --- | --- |
| M-FC1（≡ §20 M1） | supervisor 不再上报 worker 致命（`bus.report(report)` → 空操作） | `npm run test:fault-containment` | FC-01「supervisor 观察到 worker 终止」 | exit=1，命中该断言；恢复后 exit=0 |

**M2a 的结果修正了一条我自己的假设**，值得单列：第一版把「只移除显式 terminate」当作**负向对照**（预期作业对象会接管、门仍通过），实测不成立。原因是作业对象只在作业句柄关闭时动手，而句柄关闭发生在 `shutdown()` 的 `wait_exit` 之后，因此正常停机在 10 s 上界内收不回子进程（D-01 失败、进程以 23 退出），随后句柄关闭才把 sidecar 收掉（D-04/D-05 仍通过）。结论是这两个机制覆盖**不同**性质而非同一条性质的两份实现：**显式 terminate → 及时且被报告的停机；作业对象 → 强杀也不留孤儿**。该变异因此改为正向变异，判据落在 D-01。

两处因**测试自身缺陷**而重跑，如实记录：

1. **M6 第一次是假阳性**：宽松正则 `MISMATCH|digest|SHA-256` 匹配到了与本次变异无关的「缓存不存在 + `-Offline`」失败信息（其中含 `sha256` 字样）。改为精确匹配后，该变异被拆成离线/在线两种形态分别断言。
2. **M4a/M4b 第一次的失败落在 harness 上**：变异脚本的 `Invoke-Capture` 忽略了 `-WorkingDirectory`，门脚本在仓库根运行、读不到 `package.json`，于是"失败"其实是 `版本门无法读取` 这一异常，且**变异与恢复两侧都失败**。修正后两侧分别为 exit 1 与 exit 0。

M-FC1/M-FC2 亦重跑过一次：首版故障遏制脚本对「进程退出」做无界等待，导致去掉致命上报的变异体把套件挂住（§4 已记录该修正）。为避免"用不同版本的测试去证明不同的变异"，上述重跑之后的表格即为最终一致的一组证据。

`Mutation 必须验证失败发生在预期断言`这一条在本轮确实抓到了两次自己的错误，如实记录：

1. **M6 第一次尝试是假阳性**：宽松正则 `MISMATCH|digest|SHA-256` 匹配到了「缓存不存在 + `-Offline`」这条与本次变异无关的失败信息（其中含 `sha256` 字样）。改为精确匹配后，该变异被拆成两种形态（离线 / 在线）分别断言。
2. **M4a/M4b 第一次尝试的失败落在 harness 上**：变异脚本的 `Invoke-Capture` 忽略了 `-WorkingDirectory`，门脚本在仓库根运行、读不到 `package.json`，于是"失败"其实是 `版本门无法读取` 这一异常（对变异与恢复**都**失败）。修正后两侧分别为 exit 1 与 exit 0。

另外记录一条工具性教训：还原备份时 `Copy-Item` 会带回备份的**旧 mtime**，cargo 据此认为源码仍然新鲜而**不重链接**，变异二进制会存活下来（Batch 5.5 已遇到一次）。变异脚本因此在还原后显式设置 `LastWriteTime`。

### 21.5 一次实际发生的绕过（必须记录）

代码改动经 PR #5 完成，四个 required check 真实门控了它（§21.1）。但**本节的补齐提交是直接推送到 `main` 的**，GitHub 在推送时明确返回：

```text
remote: Bypassed rule violations for refs/heads/main:
remote: - 4 of 4 required status checks are expected.
```

也就是说：`required_status_checks` 只约束 PR，而 `enforce_admins=false` 使管理员可以直接推送并跳过这四个检查。这不是配置漂移（与 Batch 5.5 建立时一致，本轮未改动保护设置），而是**该配置下真实存在的绕过路径**，因此不能只写「checks 全绿」而不写这一条。绕过的那次推送本身随后仍由 push 事件触发了完整运行（run `34741760676`，四个 job 全部 success），但那是**事后验证，不是门控**——两者的强度不同，不应混为一谈。

若要消除这条路径需要 `enforce_admins=true`，那会同时阻止仓库所有者自己的直接推送，属于策略决策；本轮**未改动**该设置（用户在本轮明确要求不得关闭、绕过或临时移除分支保护，而 `enforce_admins` 的取值是既有状态而非本轮的临时手段）。

### 21.6 记账边界

本报告位于仓库内，因此**本次 §21 的补齐提交本身会触发新的 main push 运行**，而该运行的结果不可能出现在触发它的这次提交里。这与 Batch 5.5 记录的边界相同：报告的最终修订永远比它记录的最后一次远端运行晚一步。补齐提交之后的那次 main push 结果由本节的下一次修订或人工核对承接，**不在本节声称**。

## 22. 判定（§23）

```text
Known critical frontend advisory = CLOSED
Server worker fault containment  = PASS
Desktop sidecar lifecycle        = PASS
Standalone Desktop runtime       = PASS
Dataset runtime contract         = PASS
Release basemap completeness     = PARTIAL
Release city-label completeness  = PARTIAL
SCS SDK provenance               = PASS
Plugin reproducibility           = PASS
Plugin rebuildability            = PASS
Existing required CI             = PASS
P4R Batch 6A gate                = PASS
```

每一条的边界，按「它声称什么 / 它不声称什么」写明，避免把限定范围内的成立读成普遍成立：

- **advisory = CLOSED** 的范围是 `tools/ets2nav-web` 的依赖树。`tools/graph-debugger` 仍引用受影响的 unpkg 4.7.1（§2/§17）。
- **fault containment = PASS** 覆盖 worker **终止**（panic 与意外返回）。若 worker 死锁或活锁（既不终止也不推进），当前不会进入致命状态——需要心跳/看门狗，登记为 Batch 6B 项（§19.5）。
- **Desktop sidecar lifecycle = PASS** 与 **Standalone Desktop runtime = PASS** 的窗口形态（真实 WebView 渲染并连上 WS）在**本机**验证；云端 required 步骤只跑无窗口生命周期，因为 hosted runner 无交互式桌面。这两句话在报告里必须成对出现，不能只引用其一。
- **basemap / city-label = PARTIAL**：组装脚本支持并在清单里如实记录，但**当前没有随包分发**正式欧洲底图与字形资源，因此不得把这套产物描述为「完整离线地图」。
- **plugin reproducibility = PASS** 是**逐字节**意义上的（三条不同绝对路径的 clean build 相同），但**运行时行为等价未验证**（需在游戏内加载）。
- **Existing required CI = PASS** 指四个 required check 名称未变、checks 在 PR 上全绿（§21）。`Security Portable` 通过只声称 portable protocol + browser-loopback + 故障遏制 + 桌面生命周期，**不**声称完整 S1–S11 矩阵。

## 1. GLOSA 原数据链与丢失位置

审计按任务书给定的链路逐层定位（先复核源码，未采信任务书对字段的假定）。

```
nav-router::session::on_frame                      session.rs:344-393
  └─ reminder::glosa_advice(d, state, confidence, remaining, v_now, limit, cfg)
        → GlosaAdvice { v_min_kmh: i16, v_max_kmh: i16, feasible: bool }   ← 结构化值已存在
  └─ if adv.feasible && reminder_gate.allow("glosa", now_s, &speak_cfg)
        → ReminderEvent::Glosa { v_min_kmh, v_max_kmh }
NavigationSnapshot                                  session.rs:52
  └─ reminders: Vec<ReminderEvent>                  ← 唯一承载 GLOSA 的字段
server::snapshot_json                               server.rs:177
  └─ reminders[] → { kind:"glosa", severity, text: to_speech_zh(r) }
        text = "建议保持50到60"                        ← 结构化值在此被压成中文 TTS 文本
WebSocket /ws → dispatchMessage → onSnapshot → DOM
  └─ app.js 只在 !upcoming_signal 时写 $("glosa").textContent = ""   ← 从无正向写入
```

**丢失位置有两处，且互相独立**：

其一，`NavigationSnapshot` 没有结构化的 GLOSA 字段。唯一的承载路径是 `reminders`，而
`reminders` 受 §48 `ReminderGate` 节流——`SpeakConfig::min_interval_s = 30.0`。这意味着
即便 UI 去读 reminders，也只有每 30 秒中的一帧能取到值，其余帧的 GLOSA 值为空。把 UI
接在 reminders 上会得到一个「每 30 秒闪一次」的建议卡片，而这不是 UI 缺陷，是数据契约缺陷。

其二，`app.js` 从未写入 `#glosa`。原实现中该元素只在信号缺失分支被清空，正向赋值不存在；
且原实现以 `catch (e) {}` 吞掉整个快照处理异常，使这一缺失在浏览器中完全不可观测。

因此正确修法不是在 UI 侧解析 `text`，而是在 snapshot 上补一个**与 reminders 同源同帧、
但不受播报门限约束**的结构化投影。

### 1.1 顺带发现的第三个问题：绿灯窗口不可达

`glosa_advice` 本身支持绿灯窗口（`LightState::Green => (0.0, remaining)`），nav-router 单测
`glosa_green_phase` 亦证明纯函数可算出区间。但 session 中 §36/§37/§38 整块**嵌套在
`state == Red` 分支内**，故绿灯阶段 GLOSA 永不产生。该限制在 P3 关门报告中已登记
（「§38 GLOSA 仅红灯接入（绿灯窗口未接入）」），本批不改（属 §38 语义扩展，超出 Batch 2
授权范围），改为显式登记：`E2E-07e` 固定该缺口，一旦绿灯接入被实现该用例会失败并提示同步。

此项直接推翻了本批初期的一处**假信心**：我最初的 `--fake-signal` 剧本含两个绿灯阶段并
断言其产生建议，Rust 单测也只验证了纯函数——两者都"通过"，而浏览器里绿灯全程无建议。
单元测试测的是函数能力上界，不是会话可达行为；现剧本与单测均已改为断言可达性。

## 2. 新 JSON contract

`snapshot_json` 新增 `glosa` 字段，与既有字段同级：

```json
{
  "type": "vehicle",
  "upcoming_signal": { "state": "Red", "remaining_s": 12.0, "confidence": "Verified" },
  "glosa": { "min_kmh": 50, "max_kmh": 60 },
  "reminders": [ { "kind": "glosa", "severity": 0, "text": "建议保持50到60" } ]
}
```

| 情形 | 取值 |
|---|---|
| 有可行建议 | `{"min_kmh": i16, "max_kmh": i16}`，5 km/h 量化，`0 ≤ min ≤ max` |
| 无建议（无信号 / 未验证 / 黄灯 / 区间不可行 / 距离越界） | `null` |
| 字段本身 | **恒存在**，不省略——避免 UI 用 `undefined` 猜语义 |

字段命名直接沿用 Rust `GlosaAdvice.v_min_kmh` / `v_max_kmh`，只去掉类型后缀（`_kmh` 保留，
因为量纲是语义的一部分），未引入任何无意义转换。

**未输出**的字段及理由：`feasible`（字段存在本身即表示区间可行；量化已保证 `min ≤ max` 且
`min ≥ 0`，该不变量由 `glosa_advice_invariants` 单测用 1225 组参数扫描锁定，不由 UI 兜底）；
`confidence` / `target phase` / `validity`（`upcoming_signal.confidence` 与 `state` 已单独输出，
UI 不需要重复信息；内部计算状态不做无选择暴露）。

**兼容性**：`reminders`、`ReminderEvent`、`to_speech_zh` 全部保持不变，GLOSA 语音事件仍按
§48 门限节流。二者关系如下——单次计算，两个消费者，不存在第二套算法：

```
glosa_advice(...)  →  adv
                       ├─ glosa_out   → snapshot.glosa   → UI 卡片（不受门限）
                       └─ gate.allow  → ReminderEvent::Glosa → reminders → TTS（受 §48 门限）
```

结构化值先落地、再判断播报门限，因此「有建议但本帧不播报」的帧照常携带 `glosa`；
`snapshot_json_glosa_survives_speech_gate_suppression` 单测锁定这一形态。

## 3. UI 显示规则

`app.js` 新增 `formatGlosa(g)`，只消费服务端结构化字段：

| 输入 | 输出 |
|---|---|
| `null` | `""`（清空） |
| `{min:50,max:60}` | `建议 50–60 km/h` |
| `{min:50,max:50}` | `建议 50 km/h` |
| 非对象 / 非有限值 / 负数 / `min > max` | `""` + `console.warn`，**不修正** |

明确禁止的三种实现：解析 `reminder.text`、正则解析中文 TTS、从显示字符串反推速度。

信号与 GLOSA 独立判定。信号消失时 `signal-card` 隐藏、`signal-state` / `signal-remaining`

时 `#glosa` 同样清空，不保留上一帧建议。

### 4.1 replay wraparound 脆弱性（§8）

原断言在整窗口上做布尔「曾经递减」判断。改为 `RemainingRun` 状态机：遇到跳升
（`> WRAP_MIN_JUMP_M = 50 m`）即重建窗口，取历史最长连续递减段，判据为
「存在一段 ≥ 5 步的连续递减」。`wraps` 降为诊断量、不参与判定（每帧 +100 m 的单调倒退
与连续循环边界在阈值上不可区分，故 `wraps` 对大跳升序列不具诊断意义——该限制已在代码注释中写明）。

`--selftest` 提供 10 项确定性回归用例，覆盖：严格递减、跨循环边界、恒定不推进、小幅递增、
大幅递增、碎段递减（证明「出现过跳变即通过」不成立）、含未导航帧、窗口全 None、无样本、
单样本。在线观测与离线用例**共用同一 `RemainingRun` 实现**，避免两套判据漂移。

修复过程中还发现第二个脆弱点（原报告只记了 heading 一项）：**固定 60 帧观测窗口会落在
tracker 与 matcher 的启动对齐相位内**。实测 58 样本 `best_run=1` 判为失败，而同一服务器在
800 帧窗口下 `best_run=75`、remaining 11312→10521 m。故改为「观测到证据为止 + 有界预算
（900 帧 / 180 s），成功即提前返回」。**判据本身未放宽**，只是不再与 tracker 启动相位赛跑。

### 5.1 两项为 E2E 而做的产品侧修复

**`--fake-signal` 注入点从 JSON 后处理移到 session 内部。** 原实现在 `snapshot_json` 之后改写
JSON（直接覆盖 `upcoming_signal` / `map_limit_kmh`），因此 `glosa` 仍按真实（缺失的）灯态计算，
永远是 `null`——UI 的 GLOSA 卡片在该钩子下依然无法验证。现改为在 session 内注入合成灯态与
距离，reminders 与结构化 `glosa` 全部经真实 §36/§37/§38 计算。剧本 6 个阶段（红灯区间、
红灯无限速宽区间、黄灯不可行、无信号、绿灯已知缺口、红灯窄区间），每阶段 40 帧，
数值经 `glosa_advice` 反算并由 Rust 单测锁定。

**WS URL 同源推导。** `index.html` 的默认连接地址硬编码 `ws://127.0.0.1:8123/ws`，故 nav-server
监听非 8123 端口时，由该 server 自己提供的页面仍去连 8123——页面与服务端端口脱节（真实可用性缺陷，
也是动态端口 E2E 的前置条件）。现仅在页面由本机回环 HTTP 提供时改写为同源地址；`file://`
与桌面端（Tauri 非回环主机）保持原默认值，不破坏既有部署。

**`server` 子命令选项改为按名扫描。** 原实现按固定位置取 `args.get(3..6)`，单独传入的
`--port=` 会落入 replay 槽位被静默丢弃、端口回落 8123（实测：`server <ds> --port=18236`
实际监听 8123）。E2E 需要动态端口，故改为顺序无关的 `--name=value` / `--name value` 扫描，
并补上此前完全缺失的 `server` 用法行。

### 6.1 E2E-10 的产品结论

原实现 `onclose` 只把文案改成「已断开」，**不存在任何重连路径**，而 PLAN-P3plus 的 B5 验收项
明确列有「断线重连行为」。因此本轮实现最小合理方案：有界指数退避（1 s 起、上限 15 s）、
手动「连接」按钮随时可用、每次 `connect` 先作废旧 socket 并以 `isCurrent()` 门控旧事件，
不产生重复连接也不产生双份重连排程。E2E-10/10b 验证该行为，移除实现即失败。

## 7. mutation validation（§12）

### 7.1 mutation B 首轮"通过"——一次被抓住的假信心

首次运行时 mutation B 的 mutated exit 为 **0**，即破坏了 `onMapState` 而路线用例仍然通过。
根因是测试自身的缺陷：E2E-04b 原本「先用注入把折线清空、再经真实 UI 设目的地、断言折线非空」，
而页面初始化时 `route-line` 本就是空 LineString，清空是空操作；随后的非空断言由**页面自身的
HTTP 响应路径**（`setRoute`）满足，与 `onMapState` 无关。该用例名义上测 WS 路径，实际在重复
测试 HTTP 路径。

修正后，E2E-04b 的判据变为：用 UI「清除」按钮置空 → 用 `fetch` 直接 POST（页面不经手响应）
→ 折线若重新非空，唯一来源只能是 `onMapState`。修正后 mutation B 的 mutated exit 为 1。

这正是任务书要求 mutation validation 的原因：四个用例里有一个原本不具备检测能力，而它在
正常运行时是"绿"的。
